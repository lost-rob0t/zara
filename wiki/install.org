#+title: Install, Build, and Validate Zara
#+options: toc:3 num:nil

* The supported path is Nix

Zara targets Linux and uses its flake as the authoritative dependency, development, package, and test definition.

If you are trying to understand settings rather than install software, go to [[file:../docs/configuration.org][configuration.org]]. The annotated config files are [[file:../docs/config/main.org][main TOML]], [[file:../docs/config/prolog.org][Prolog]], and [[file:../docs/config/mcp.org][MCP]]. This page used to contain half the application's configuration manual. It has been relieved of that duty.

** Requirements

- Nix with flakes enabled.
- Linux on a supported flake system (=x86_64-linux= or =aarch64-linux=).
- Working audio devices if you intend to use voice modes.
- Network access when Nix/model/provider dependencies need it.

* Development checkout

#+begin_src sh
git clone https://github.com/lost-rob0t/zara.git
cd zara
nix develop
#+end_src

The development shell supplies the Python, SWI-Prolog, audio, Qt, MCP, STT, and test dependencies expected by the repository.

Inside =nix develop=, the development wrappers execute the working checkout rather than an immutable packaged copy. That is what you want while changing code, unless debugging the wrong tree sounds entertaining.

* Build

Build the default package set:

#+begin_src sh
nix build
#+end_src

The flake packages Zara's Python runtime and Prolog resources together and supplies required executable dependencies through Nix wrappers.

Useful packaged applications include the unified CLI, desktop, wake, dictation, and console-related package surfaces. Use [[file:../docs/cli.org][cli.org]] for the command matrix rather than maintaining two competing lists here.

* Run

Default CLI/help:

#+begin_src sh
nix run
#+end_src

Desktop:

#+begin_src sh
nix run .#zara-desktop
#+end_src

Wake mode:

#+begin_src sh
nix run .#zara-wake
#+end_src

Dictation:

#+begin_src sh
nix run .#zara-dictate
#+end_src

For arguments to the unified app, pass them after =--=:

#+begin_src sh
nix run .#zara -- --wake --pets --stt-provider faster-whisper --model small
#+end_src

See [[file:../docs/cli.org][CLI and entry points]] and [[file:../docs/STT.md][STT backends]].

* Configuration created on first run

The normal main config is:

#+begin_example
$XDG_CONFIG_HOME/zarathushtra/config.toml
#+end_example

or, without =XDG_CONFIG_HOME=:

#+begin_example
~/.config/zarathushtra/config.toml
#+end_example

Zara creates the main TOML when it does not exist. Invalid existing TOML is reported as an error; it is not silently thrown away and regenerated.

Other user-facing configuration layers:

- Prolog user facts/mappings: see [[file:../docs/config/prolog.org][config/prolog.org]].
- MCP management overlay: =~/.config/zarathushtra/mcp.toml=; see [[file:../docs/config/mcp.org][config/mcp.org]].

The complete explanation is in [[file:../docs/configuration.org][configuration.org]].

* Voice setup

The default generated config selects local faster-whisper STT and a configured TTS provider. Voice behavior is split deliberately into separate docs:

- [[file:../docs/voice.org][voice.org]] — microphone, VAD, acknowledgement, routing, TTS, barge-in, latency.
- [[file:../docs/STT.md][STT.md]] — faster-whisper, whisper.cpp, OpenAI Whisper, sherpa model families, OpenAI/Groq transcription.
- [[file:../docs/config/main.org][config/main.org]] — the actual settings.

Whisper.cpp is available as Zara's Vulkan-capable local path. The flake includes a Vulkan-enabled whisper.cpp package so AMD acceleration does not depend on pretending every GPU API is CUDA.

* Models and remote providers

Some model assets are fetched/managed by their backend and some are intentionally explicit local paths.

- faster-whisper named models use Zara's normal observable model/cache path.
- whisper.cpp uses a GGML model file/path.
- sherpa-onnx model families expect explicit model directories and are not silently downloaded by Zara.
- OpenAI transcription requires =OPENAI_API_KEY=.
- Groq transcription requires =GROQ_API_KEY=.
- conversational OpenAI/Anthropic providers use their normal API key environment/config path.

Provider-specific examples live in [[file:../docs/STT.md][STT.md]] and [[file:../docs/config/main.org][the main config guide]].

* Full regression gate

Repository work is not finished because one targeted pytest passed.

Run the full fail-fast gate:

#+begin_src sh
nix develop -c bash scripts/test-all.sh
#+end_src

Then run flake checks:

#+begin_src sh
nix flake check
#+end_src

The repository gate covers the important layers, including Python compile/import, Prolog loading, pytest, security/regression scripts, deterministic latency checks, entry points, and packaging. Exact phases evolve with the repository; =scripts/test-all.sh= is the executable source of truth.

GitHub pull requests/pushes also need the Actions test job to pass at the exact head being proposed. An old green run on an older SHA is decorative, not evidence.

* Targeted tests

Run one Python test file:

#+begin_src sh
nix develop -c pytest t/test_agent_history.py
#+end_src

Run one test node:

#+begin_src sh
nix develop -c pytest t/test_agent_history.py::test_multiple_results_survive_in_call_order
#+end_src

Shell/integration checks live under =scripts/test-*.sh=. Do not replace the full gate with one of them for final validation.

* Voice latency regression

Wake mode can record payload-free JSONL timing metrics. The default location is:

#+begin_example
$XDG_STATE_HOME/zarathushtra/latency.jsonl
#+end_example

falling back to:

#+begin_example
~/.local/state/zarathushtra/latency.jsonl
#+end_example

Run the deterministic latency metric check:

#+begin_src sh
nix develop -c bash scripts/test-latency-metrics.sh
#+end_src

Generate a fixture-backed benchmark report:

#+begin_src sh
python scripts/benchmark-voice.py \
  --jsonl /tmp/voice-latency.jsonl \
  --report /tmp/voice-latency-report.json
#+end_src

The benchmark separates cold/warm cohorts and reports distribution statistics/stage dominance. Provider LLM latency is report-only rather than forced under a fictional universal internet SLA.

Metrics contain timing/stage metadata, not transcript text, prompts, credentials, or audio bytes. See [[file:../docs/voice.org][voice.org]].

* Packaging checks

The Nix build is the supported package path. It bundles the Prolog tree in the layout expected by the Python runtime.

Zara also ships =setup.py= and =MANIFEST.in= as a best-effort Python packaging companion. A wheel/sdist can install Python modules, console scripts, and Prolog resources under =<sys.prefix>/share/zarathushtra/=.

That does *not* mean =pip install .= can conjure SWI-Prolog, audio backends, local model binaries, Qt platform support, and every native dependency correctly on an arbitrary machine.

If you deliberately use the unsupported Python path:

#+begin_src sh
python -m venv .venv
source .venv/bin/activate
pip install .
#+end_src

There is no separate authoritative =requirements.txt=. Dependency definitions are maintained in =flake.nix= and packaging metadata.

* Runtime resource lookup

Packaged code searches supported locations for =main.pl= so the same runtime can work from a checkout, a Nix package, or the best-effort Python installation layout.

Normal development should not need hand-written =PYTHONPATH= / SWI paths. If it does, first check whether you accidentally left the Nix environment or are invoking an unwrapped interpreter.

* Linux desktop notes

The native desktop and Pets use PySide6/Qt6.

Pets have additional X11/Wayland overlay behavior documented in [[file:pets.org][wiki/pets.org]] and [[file:../docs/pets.md][docs/pets.md]]. The desktop application itself is documented through [[file:../docs/features.org][features.org]] and [[file:../docs/architecture.org][architecture.org]].

Linux is the tested platform. Python/Qt portability does not constitute a support contract for macOS or Windows.

* Troubleshooting order

When a development checkout fails, check these in order:

1. Are you inside =nix develop= or using a Nix app wrapper?
2. Does =nix flake check= evaluate/build the relevant check?
3. Does =scripts/test-all.sh= identify a specific failing phase?
4. For Prolog failures, does =main.pl= consult cleanly?
5. For STT failures, confirm provider/model/device in [[file:../docs/STT.md][STT.md]].
6. For microphone/VAD/TTS failures, use [[file:../docs/voice.org][voice.org]].
7. For MCP failures, use =zara mcp status= and [[file:mcp.org][mcp.org]].
8. For configuration failures, use [[file:../docs/configuration.org][configuration.org]].
