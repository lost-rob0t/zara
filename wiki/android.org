#+title: Zara Android client

* Status vocabulary

This page is an Android implementation/status companion to [[file:../docs/book.org][The Zara Book]]. Current source and tests outrank roadmap prose.

- *IMPLEMENTED* — present in current code with repository build/test evidence.
- *ACTIVE / EVOLVING* — real foundations exist, but the user-facing workflow is still changing.
- *GATED / PLANNED* — designed, proposed, or partially implemented; do not rely on it as shipped behavior.
- *HARDWARE / VENDOR-GATED* — repository contracts exist, but physical-device or vendor-controlled acceptance is still required.

* Overview

Zara Android is a native client under =android/=. Fresh installs are intentionally *local-first*: the phone can use its portable Prolog/runtime foundation without first enrolling with a remote =zara-server=. Remote mode remains an explicit authenticated option rather than a prerequisite for opening the app.

Android is still *ACTIVE / EVOLVING* as a complete daily-driver assistant. Several foundations are already implemented and should not be described as merely planned, while physical-device/vendor claims remain separate from JVM/emulator/build evidence.

* Architecture: local and remote are explicit modes

#+begin_example
                     Zara Android UI
                           |
                    AndroidAppSession
                      /           \
             Local mode            Remote mode
                |                      |
      Trealla / LocalAiService       ZaraClient
                |                      |
     typed device capabilities    CURVE/ZAP ZARA/1
                                       |
                                  zara-server
                                       |
                                  RuntimeHost
#+end_example

Local mode is not a fake disconnected form of Remote mode. It owns explicitly local symbolic/model/device work. Remote mode connects to the canonical server authority through the authenticated client boundary.

No local model failure should be documented as a successful cloud fallback. No remote capability should be implied to exist while offline. Switching modes must remain visible rather than silently uploading local state.

* Toolchain and build

The Android toolchain is pinned through Nix and Gradle. Current documented values include Gradle 9.5.1, Android Gradle Plugin 9.2.0, JDK 21, compileSdk 37, targetSdk 36 and minSdk 29.

Run the Android repository gate with:

#+begin_src sh
nix develop ./android -c bash scripts/test-android.sh
#+end_src

The normal debug APK is:

#+begin_example
android/app/build/outputs/apk/debug/app-debug.apk
#+end_example

Release/distribution architecture is itself evolving under the fleet release lane. Do not infer immutable release semantics from a green master build. For any downloadable artifact, prefer exact source SHA, signer/checksum evidence, and the currently documented release channel over stale version prose.

* Portable Prolog / Trealla

*IMPLEMENTED FOUNDATION*

Android runs an explicitly portable Prolog subset through Trealla. The boundary remains intentionally thin: app-private source/workspace state, JNI for native execution, Kotlin typed wrappers, and deterministic semantic fixtures.

The goal is semantic parity for the portable subset, not pretending Trealla and server-side SWI-Prolog have identical APIs.

* Local-first runtime and embedded AI

** Local runtime selection

*IMPLEMENTED*

Fresh installs default to =Local=. A legacy unversioned Remote preference is migrated once to Local so an upgraded phone is not stranded behind missing server enrollment. A new explicitly selected Remote mode is versioned and remains explicit.

Local mode does not manufacture a fake CURVE server pin. Server trust material belongs to Remote mode.

** Embedded local AI

*IMPLEMENTED FOUNDATION + HARDWARE/MODEL EVIDENCE EVOLVING*

The app owns a non-exported =LocalAiService= and an offline-only =Embedded Local= language-model provider. The provider contract includes model catalog/listing, verified install, selection, streaming generation, cancellation and unload. Model files live in app-private storage and are checked against declared identity/version/format/quantization/context/backend/SHA-256 metadata before activation.

Language-model and speech provider families are separate. The initial offline TTS path uses an installed Android voice that does not require a network connection.

The built-in embedded language-model runtime currently executes the LiteRT-LM format. The shared descriptor can represent other formats for future providers, but a descriptor is not execution support.

Real model quality, cold/warm latency, peak RSS, thermals, battery use and device compatibility remain model/device evidence, not something a JVM contract can prove.

* Authentication and remote mode

*IMPLEMENTED FOUNDATION + ACTIVE / EVOLVING continuity*

Remote Android uses server-key pinning, client identity, JeroMQ CURVE/ZAP authentication and explicit server enrollment. A changed server key fails closed rather than silently repinning.

The server must expose an authenticated TCP endpoint in addition to its normal owner-private local IPC. The expert/manual server shape remains:

#+begin_src sh
zara-server --remote-endpoint tcp://<LAN-IP>:6060 --security-dir <PRIVATE-DIR>
zara-server --security-dir <PRIVATE-DIR> --security-init
zara-server --security-dir <PRIVATE-DIR> --security-show-public-key
zara-server --security-dir <PRIVATE-DIR> \
  --security-enroll-key <Z85-CLIENT-PUBLIC-KEY> \
  --security-device-id <DEVICE-ID>
#+end_src

Preparing phone identity and pinning a server key is not proof that the server enrolled the device or that a live session exists. Keep identity-created, server-pinned, enrolled, connecting, connected and rejected/degraded states distinct.

* Prolog automation and Android authority

*IMPLEMENTED FOUNDATION; HIGHER AUTHORITY ACTIVE / GATED*

The merged local automation foundation exposes a closed =automation/2= plan with typed actions rather than raw shell/Intent execution. Examples include semantic app opening/search, URI opening, bounded Accessibility selectors/actions and reviewed global actions.

#+begin_src prolog
automation(youtube_psytrance,
    actions([app_search(youtube, "psytrance")])).
#+end_src

Android remains the authority for special access. Zara can take the user to Assistant, Accessibility, Usage Access, Write Settings, or Overlay grant surfaces; a Prolog rule cannot self-grant those privileges.

Do not confuse the merged typed =standard=/existing automation substrate with proposed unrestricted/root/Shizuku/device-owner authority. Those broader authority contracts remain subject to their live fleet vote, implementation and hardware evidence.

* Installing Zara Wear from the phone

*IMPLEMENTED FOUNDATION; PHYSICAL-WATCH ACCEPTANCE HARDWARE-GATED*

The phone app contains a Watch Setup workflow that discovers Bluetooth-paired watches, Wear Data Layer nodes, and Wireless ADB endpoints. Wireless ADB is used for installation; normal phone↔watch communication can return to Bluetooth/Wear Data Layer afterward.

A practical install flow is:

1. Pair the Wear OS watch with the phone normally.
2. Open *Zara Watch Setup* on the phone and allow Nearby/Bluetooth permissions when Android asks.
3. On the watch, enable Developer options and *Wireless debugging*.
4. Scan from Zara. A Bluetooth/Data Layer watch may be visible before an ADB endpoint is available.
5. Choose/use the watch pairing endpoint, enter its IP, pairing port and current six-digit pairing code, then pair.
6. Return to the watch Wireless debugging screen and use its separate connection port to connect.
7. Tap *Install Zara Wear*. Zara downloads the rolling Wear APK through the repository helper, verifies the expected artifact/checksum contract, pushes it to the watch and invokes the watch package manager.
8. After an explicit successful install result, disconnect ADB. The setup flow then rechecks Wear discovery; Bluetooth/Data Layer is the normal phone↔watch path.

The installer also recognizes/removes the legacy =ai.zara.wear= package after installing the current app identity.

This repository flow does *not* prove Galaxy Watch5 Pro button mapping, microphone/speaker routing, battery behavior, nearby transport under real disconnect/reconnect, or package update behavior on physical hardware. Those remain human/device acceptance gates.

* Samsung Health

*IMPLEMENTED FOUNDATION; HARDWARE / VENDOR-GATED*

Current master includes a read-only Samsung Health integration driven through the existing local Prolog runtime. It exposes readiness, granted permissions and today's steps, sleep duration, heart-rate minimum/maximum, and exercise duration/calories.

The default editable source is =samsung_health.pl=. It resolves only to a closed =samsung_health_action(...)= vocabulary; arbitrary Prolog terms are not translated into vendor SDK calls. A single-thread actor serializes physical reads, and a missing permission fails before the read reaches the vendor gateway.

Samsung's Data SDK is an optional local AAR and is intentionally not committed. With no matching =android/app/libs/samsung-health-data-api-*.aar=, ordinary builds remain valid and the typed gateway reports =SDK_MISSING=. With the vendor AAR present, the SDK adapter is compiled.

Permission acquisition is an explicit foreground Activity/user-consent boundary. SDK readiness, app/package authorization and per-data-type permission are separate states.

Do not report the JVM contract as real Samsung Health acceptance. Vendor/device proof requires a compatible physical device, official AAR, supported Samsung Health version, actual permission grant/deny/revoke checks and any required package/signing authorization. The integration is fitness/wellness data only; it does not add diagnosis or treatment behavior.

See [[file:android-samsung-health.org][android-samsung-health.org]] for the detailed Prolog/SDK contract.

* Chat, voice and product UI

*ACTIVE / EVOLVING*

The native app has real runtime/UI foundations, but the complete daily-driver product shell continues to change. Current accepted navigation/product designs must not be labeled merged until their implementation lands on master.

Android device edges own microphone/speaker, OS assistant entry points and permissions. Local symbolic/model operation can work without the server; connected shared-runtime work uses the authenticated Zara client/server boundary.

UI recreation must never create a second assistant authority or silently duplicate submitted work.

* Security rules

Android work must preserve these user-visible invariants:

1. no long-lived secrets embedded in APK assets/source or exposed in routine logs/screenshots;
2. changed/unexpected server pins fail closed;
3. display strings/model text/plugin payloads never override authenticated principal or local privilege authority;
4. capability availability is not authorization;
5. Android permissions/special access remain explicit platform grants;
6. stale session/generation events cannot mutate current state or execute stale effects;
7. malformed/oversized protocol, Prolog-effect and vendor payloads stay bounded;
8. local model failure does not silently become cloud success;
9. emulator/JVM evidence is never reported as physical-device acceptance.
