#+title: Zara Android client

* Overview

The native Android Zara client lives under =android/=. It is a client of the same Zara runtime/service architecture used by Linux rather than a second mobile-only assistant implementation.

The Android project is currently *active / evolving*. Core foundations are real and tested, but the complete daily-driver assistant surface is still being built.

Parent work includes the Android epic/issues around #152, #170–#179, later assistant/UI slices, and Samsung integration work.

* Build and test

Run the Android repository gate with:

#+begin_src sh
nix develop ./android -c bash scripts/test-android.sh
#+end_src

The gate is intended to cover the JVM/unit/build path plus the APK secret-marker inspection used by the repository.

The debug APK is produced at the standard Gradle location:

#+begin_example
android/app/build/outputs/apk/debug/app-debug.apk
#+end_example

The dedicated Zara Code Editor APK is produced at:

#+begin_example
android/code-editor/build/outputs/apk/debug/code-editor-debug.apk
#+end_example

The Android gate verifies the APK signature and manifest/package identity, and
CI installs and launches =ai.zara.code.editor= on an emulator. The rolling
=android-latest= publication path additionally verifies that Zara Code carries
the repository's update-compatible signing certificate before publishing
=zara-code-editor-latest.apk=.

If Android asks to update an older Zara Code development build and then reports
that the package appears invalid, the installed development build may have been
signed with a different ephemeral debug certificate. Android cannot replace an
installed package with the same application id under a different signing key.
Uninstall the old =ai.zara.code.editor= build once (Settings > Apps > Zara Code
> Uninstall, or =adb uninstall ai.zara.code.editor=), then install the current
=zara-code-editor-latest.apk=. Rolling and immutable publication keep signer
continuity after that migration.

Zara product/version state is centralized in the repository-root
=version.properties=. =zara.version= and =android.versionCode= identify the
source currently being built; =release.target= and
=release.targetAndroidVersionCode= identify the active release line. Inspect
the validated machine-readable context with:

#+begin_src sh
python scripts/version-context.py --format json
#+end_src

Python packaging, the phone APK, and the Wear APK consume the current values
from that file. A =master= push validates the context but does not mint an
immutable versioned release. The separately gated =android-latest= channel
remains mutable and points at the latest fully green master artifact.

An immutable alpha is published only from an explicit =v*= tag whose name
matches the current product version *and* only after the current version/code
have been promoted to the active target (=release_ready=true=). The release
workflow loads the update-compatible debug signing key from
=ZARA_ANDROID_DEBUG_KEYSTORE_B64=, verifies the APK signing certificate, and
attaches the APK, checksum, and provenance manifest. The release APK remains a
sideloaded debug build; hardware and Assistant-role acceptance remain separate.

A successful =assembleDebug= is necessary, but it is not acceptance for the whole Android assistant.

* Portable Prolog / Trealla

Android uses Trealla for the portable symbolic subset selected during the Android runtime bakeoff.

The boundary is intentionally thin:

- portable Prolog source is staged from application assets;
- JNI exposes the minimal native execution bridge needed by Android;
- Kotlin wraps that bridge in typed application code;
- deterministic semantic fixtures compare expected behavior;
- portable rules should not accidentally depend on SWI-only features.

The goal is semantic parity for the explicitly portable subset, not API parity between SWI-Prolog and Trealla.

Core/Linux Zara continues to use SWI-Prolog through the Python application boundary.

* Authentication and enrollment

Android uses the same Zara daemon identity model as other authenticated clients.

Merged/current foundations include:

- Android-side credential encryption/storage boundary;
- typed enrollment state/repository code;
- client key material handling;
- daemon public-key pinning;
- JeroMQ CURVE socket configuration;
- Z85 key exchange helpers;
- bounded plaintext secret lifetime during enrollment operations;
- explicit rejection of silent server repinning.

The important rule is *fail closed on server identity changes*. A changed server key is not silently accepted as "probably the same server."

The phone needs an explicit authenticated TCP listener; the default Zara service
listens only on owner-private local IPC. Start the service with
=--remote-endpoint tcp://<LAN-IP>:6060 --security-dir <PRIVATE-DIR>= to keep
local IPC available for the desktop and wake clients while enabling Android.
Initialize the owner-private security directory with =zara-server
--security-dir <PRIVATE-DIR> --security-init= while the service is stopped.
Show its public key with =--security-show-public-key= and pin that key in the
Android Settings screen. Enroll the phone's CLIENT PUBLIC KEY with
=--security-enroll-key <Z85-KEY> --security-device-id <DEVICE-ID>=. The phone's
"enrollment ready" label only confirms local identity and server pinning; it
does not confirm server-side authorization or a live connection.

Settings shows the saved server public key after enrollment. If it differs
from the running server's public key, "Change trusted server key" requires an
explicit replacement key. It preserves the Android client identity but drops
the old session and conversation; reconnect from Remote afterward. Remote
shows =server_hello_timeout= for a hello timeout and
=capability_negotiation_timeout= for a later capability timeout. These labels
contain no credentials or raw exception messages.

Issue #173 remains reopened because the full client acceptance is larger than the merged auth primitives. Remaining/continuing work includes complete authenticated connect/hello behavior, reconnect, durable session/conversation continuity, stale-session rejection, and ordinary typed turn/event integration across lifecycle changes.

* Runtime state

Android client state should remain typed and reducer-driven rather than letting Activities/Composables each invent their own connection/assistant truth.

State should represent facts such as:

- disconnected / connecting / authenticating / connected / degraded states;
- current server/enrollment status;
- active session/conversation identifiers where valid;
- current turn/activity state;
- capability negotiation results;
- explicit errors that can be rendered honestly by UI.

UI recreations must not create a new assistant authority or silently duplicate submitted work.

* Remote protocol truth and typed failures

The Android client speaks the same =ZARA/1= vocabulary the server emits:
=voice.speech.started=, =voice.speech.ended=, =turn.cancelled=,
=runtime.error=, and =runtime.stopped= are decoded rather than rejected, and
legal text frames interleaved into the voice stream are tolerated. Wire
failures carry stable typed codes (for example =protocol.malformed=,
=protocol.unexpected_message=, =protocol.stale_generation=,
=protocol.version_mismatch=, =protocol.server_error=, =transport.timeout=,
=transport.closed=, =remote.not_connected=) plus the server's own error code
and retryability when present.

Invariants:

- handshake and =turn.accepted= retain a five-second response deadline, while
  an accepted text turn allows up to 30 minutes between generation events so
  complex work is not misclassified as a dead transport;
- a failed frame can never leave the client in a fake-connected state;
  session-desyncing failures collapse the connection into the bounded
  reconnect with a typed reason;
- stale frames from a previous session/generation are fenced: they are
  recorded as =protocol.message.rejected= telemetry and dropped without
  corrupting the current session;
- the persisted remote session is restored on launch (=session.restore.*=
  events) instead of silently remaining disconnected after process
  recreation;
- every connected-to-disconnected transition has exactly one typed terminal
  event with the same correlation/generation.

Chat failures render one structured error card (subsystem, operation, typed
code, connection state, recovery, incident id, Retry/Reconnect/Diagnostics)
and the footer separates mode, authentication, and transport truth
(=REMOTE • AUTHENTICATED • CONNECTED/RECONNECTING/DISCONNECTED • SYMBOLIC=);
authentication validity is never presented as a live connection.

* Diagnostics

=ZARA-LOCAL-DIAGNOSTICS/2= is the current export: a deterministic text and
canonical-JSON incident bundle with a retained =primary_failure= block
(subsystem, operation, phase, typed code, bounded sanitized message/cause,
first/last seen, request/turn correlation, last successful step, recovery),
remote/protocol context (transport kind, connect generation, last
connected/disconnected timestamps, negotiated protocol version, handshake
state, close code and bounded reason, last RX/TX message metadata, expected
next state, last completed turn), voice pipeline stage states with explicit
=not_applicable= semantics, and a correlated ordered timeline from the typed
telemetry journal. Protocol message records carry metadata only (type,
sequence, size) — never payloads, credentials, audio, or prompt/response
text.

The deterministic regression layer for this contract is
=android/integration/remote_recovery_fixture.py= (failure injection: =ARM
MALFORMED|VERSION_MISMATCH|OUT_OF_ORDER|CLOSE|STALE=) driving the real
client in =RemoteRecoveryInteropTest= and the installed APK in
=device_remote_recovery_acceptance.py=.

* Chat / assistant surface

The native chat/assistant UI is still active work.

The intended direction is:

- real Android UI rather than an embedded web app;
- one durable conversation model compatible with desktop/server history;
- streaming assistant updates;
- explicit cancellation;
- clear connection/auth states;
- voice and typed turns sharing durable conversation identity;
- Android system-assistant integration without bypassing =ZARA/1= runtime semantics.

Do not fork protocol message types just because Compose needs a particular widget state. Adapt canonical runtime events into presentation state.

* Android Assistant role / voice

The Android goal includes integration with Android's assistant/voice surfaces where supported by the target API level.

The ownership model remains:

- Android device owns microphone/speaker and OS-level assistant entry points;
- =zara-server= owns the shared assistant runtime work;
- local wake/system activation may start a Zara voice session;
- voice transcript and assistant output should correlate with canonical conversation/turn ids.

The exact Android system-service implementation remains active work and should not be claimed as shipped until the relevant acceptance tests pass.

* Device integrations

Planned/follow-on integrations include Samsung/SmartThings, Termux, and other device-local capabilities.

These should be modeled as explicit capabilities/adapters and routed through Zara's normal authorization/runtime model. They should not become arbitrary hidden side effects attached to chat parsing.

* Security rules

Android-specific work must preserve these rules:

1. no long-lived secret keys/tokens embedded in APK assets or source;
2. no private key material in logs, crash text, diagnostics, screenshots, or test artifacts;
3. changed/unexpected server pins fail closed;
4. caller-supplied display/user strings never override the authenticated principal;
5. stale connection/session events cannot mutate current state;
6. reconnect must not duplicate side-effecting requests;
7. malformed/oversized protocol input remains bounded;
8. phone UI/process lifecycle must not be treated as proof that the daemon session or turn resumed.
