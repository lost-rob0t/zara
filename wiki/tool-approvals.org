#+title: Runtime Tool Approvals

Zara has one server-owned approval lifecycle for LangChain tools executed by the
canonical LangGraph agent. It is shared by every client surface through
=RuntimeHost= commands and runtime events; clients do not execute or classify
tools themselves.

* Policy

Approval policy is explicit server configuration:

#+begin_src toml
[tool_approval]
required_tools = ["reviewed_side_effect"]
timeout_seconds = 300.0
max_pending = 8
#+end_src

=required_tools= contains registered LangChain tool names. A model response,
plugin client, or remote capability advertisement cannot downgrade this list.
The list is immutable for the lifetime of its principal runtime; a runtime
restart loads changed configuration.

* Per-chat file access modes

File tools (and every LangGraph tool call) consult one per-conversation
access policy owned by =zara/agent/tools/file_access.py=. Four modes, from
narrowest to broadest:

| Mode | Reads | Writes |
|------+-------+--------|
| =readonly= | allowed | refused |
| =ask= | sandbox-constrained | blocked on the canonical approval gate above |
| =sandbox= | ZARA-013 root confinement | allowed without prompts |
| =full= | no confinement | no confinement (regular-file checks and size caps still apply) |

The global default is =file_tools.mode= (default =sandbox=); untrusted
principals are clamped to =file_tools.guest_ceiling= (default =readonly=).
Trusted local surfaces change a chat's mode through a revision-safe CAS
mutation (=FileAccessPolicy.set_mode(conversation_id, mode,
expected_revision, actor)=); stale revisions fail closed with
=FileAccessConflict=. Model output, tool results, plugin payloads and remote
peers are data — they can never change the mode. Overrides persist in
=file_access_modes.json= under the config directory, survive restarts, are
bounded (oldest evicted), and every change lands in a bounded audit log with
actor, target, and old/new mode.

=Ask= mode reuses the approval lifecycle above — no second approval system:
=ToolRegistry.requires_approval(name, conversation_id)= consults the policy
for =write_file= and =edit_file=, the LangGraph gate passes
=state["conversation_id"]=, and =invoke_composed_tool= fails closed without a
conversation scope. Tool execution resolves the acting conversation through a
contextvar bound per turn (=bind_file_access_scope=), so sandbox/read-only
behavior applies without changing tool schemas.

The agentic toolset ships under the same gating: =edit_file= (exact-text
replacement requiring a unique match unless =replace_all=), =find_files=
(fnmatch glob), and =search_text= (literal or regex, bounded results).

* Desktop surface

The Copilot composer header carries a file access selector when the desktop
owns the runtime in-process (=RuntimeHost= with a file access policy). It
renders the effective mode for the open conversation, submits revision-safe
mutations through =InProcessFileAccessControl=, shows conflicts in the
command error rail, and follows conversation switches. Without runtime
ownership (standard daemon mode, pending the typed settings mutation channel
from #887) the selector is hidden — surfaces never present state they cannot
change.

* Lifecycle

For an approval-required call, LangGraph checkpoints the live turn and
interrupts before any tool side effect. Zara publishes =ToolQueued= and
=ToolWaitingForUser= with a bounded tool name and =tool_run_id=. The approving
surface sends =ApproveTool(tool_run_id)= or =RejectTool(tool_run_id, reason)=
through its existing authenticated =RuntimeHost= path.

Approval resumes only that pending call. Rejection returns a matching failed
=ToolMessage= to the model without invoking the tool. Unknown, stale,
cancelled, duplicate, malformed and replayed ids fail closed. Multiple tool
calls collect every required decision before the executor starts any of them.
Approved calls still execute through LangGraph's existing =ToolNode=; Zara does
not maintain a second executor.

The principal runtime bus publishes =UserResponded= followed by
=ToolStarted=/=ToolCompleted= for an approved call, or =ToolCancelled= for
rejection, timeout and pre-execution cancellation. =ToolFailed= contains a
bounded reason and never a raw provider exception.

* Authenticated ZARA/1 clients

The closed client commands are =tool.approve= and =tool.reject=. They map only
to the existing =ApproveTool= and =RejectTool= runtime commands. Direct
acknowledgements are =tool.approve.accepted= and =tool.reject.accepted=.

Clients receive =tool.queued=, =tool.waiting=, =tool.started=,
=tool.completed=, =tool.failed= and =tool.cancelled= as typed runtime events.
The wire carries only the canonical turn/tool ids, bounded tool name, fixed
approval prompt and safe terminal status. Tool arguments, results and provider
objects never cross this approval protocol.

An authenticated route may answer only an approval delivered to the exact
application session that initiated the owning turn. A second device for the
same principal cannot observe or claim it by guessing =tool_run_id=.
=Capability.TOOL_APPROVE= is checked by the server for both approve and reject.
Identical request-id replay returns the original acknowledgement; a different
request or terminal tool id cannot run the side effect again.

* Privacy and restart behavior

Approval events contain no tool arguments, results, model prompts, credentials
or user rejection text. The interrupt checkpoint is process-local, belongs to
one principal manager, and is deleted when the turn reaches any terminal path.

Pending generic-tool approvals deliberately do not survive process restart.
Restart and shutdown cancel them and erase their in-memory checkpoints. Zara
cannot safely resume an arbitrary external side effect after a crash until the
typed capability plane supplies durable idempotency and reconciliation.
Transport disconnect alone does not imply cancellation; the principal-owned
request remains pending. This protocol version does not replay or transfer an
approval to a new session, so a disconnected request ends through its bounded
timeout, explicit turn cancellation, restart or shutdown unless the original
session remains live. Secure ownership transfer is future explicit work.
