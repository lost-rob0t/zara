* What a plugin is allowed to be

Zara supports small tool modules and versioned long-running service plugins.

The important constraint is what a plugin is *not*: it is not a second Zara runtime. It should not create its own event bus, speech pipeline, timer scheduler, notification subsystem, agent, or secret route into Qt internals.

Service plugins get a narrow facade over [[file:../docs/architecture.org][RuntimeHost]]. That keeps an external integration useful without making every plugin a new architecture.

* Discovery

Zara discovers public =*.py= files in =[modules].search_paths= directories. The generated config includes:

#+begin_example
~/.zarathushtra/plugins/
~/.zarathushtra/modules/
#+end_example

Files beginning with =_= are ignored. Discovery is deterministic and local. Zara does not automatically download, update, package, or bless whatever it finds there.

Configure paths under:

#+begin_src toml
[modules]
search_paths = [
  "~/.zarathushtra/plugins",
  "~/.zarathushtra/modules",
]
autoload = []
#+end_src

* Legacy tool plugins

Existing tool-only modules remain supported. Export one of:

#+begin_src python
def register_tools(prolog_engine):
    return [some_langchain_tool]


def register_skills(prolog_engine):
    return [some_langchain_tool]
#+end_src

Returned objects must be LangChain =BaseTool= instances and tool names must be unique.

This API is intentionally small. If you only need a callable tool, do not invent a long-running service because threads are available and therefore apparently irresistible.

* Service plugin API version 1

A long-running integration exports one factory. Importing the module must *not* start threads, network servers, child processes, subscriptions, or other resources. Import discovers the plugin; =start()= starts it.

#+begin_src python
import queue

from zara.plugins import PluginMetadata, ServicePlugin


class EventObserver(ServicePlugin):
    metadata = PluginMetadata(
        name="event-observer",
        version="1.0.0",
        api_version="1",
        description="Counts provider-neutral runtime events.",
    )

    def __init__(self):
        self.subscription = None
        self.worker = None
        self.events_seen = 0

    def start(self, runtime):
        if not runtime.configuration.get("enabled", True):
            return
        self.subscription = runtime.subscribe(maxsize=64)
        self.worker = runtime.start_worker("events", self.consume_events)

    def consume_events(self, stop_event):
        while not stop_event.is_set():
            try:
                self.subscription.get(timeout=0.25)
            except queue.Empty:
                continue
            self.events_seen += 1

    def stop(self):
        pass


def create_plugin():
    return EventObserver()
#+end_src

=create_plugin()= is called once for a =RuntimeHost= lifecycle. =start(runtime)= runs after the runtime backend is ready. =stop()= runs during shutdown/restart or cleanup after failed startup. A fresh runtime lifecycle creates a fresh plugin instance.

A service may implement =tools()= and return normal LangChain =BaseTool= objects. Zara registers those before =start()= and removes them if the service fails/stops. The current LangGraph backend supports service tools; a backend that cannot register tools is allowed to reject that optional capability without killing the rest of Zara.

* PluginRuntime facade

The object passed to =start()= is a per-plugin facade, not =RuntimeHost= itself.

** =status=

Returns a snapshot containing runtime state/aliveness/thread identity useful for health reporting.

** =configuration=

Returns a copy of only:

#+begin_example
[plugins.<plugin-name>]
#+end_example

The plugin does not receive every Zara setting merely because reading dictionaries is easy.

** =dispatch(command)=

Submits a canonical =zara.runtime.commands.RuntimeCommand= through =RuntimeHost= and returns a =concurrent.futures.Future=.

A plugin should handle =UnsupportedRuntimeCommand= for optional commands. Current runtime interfaces deliberately contain some hooks that the LangGraph backend does not implement yet.

** =subscribe(maxsize=N)=

Returns an ordered =RuntimeEventSubscription= backed by a bounded queue.

Rules:

- size must be 1 through 4096;
- when full, the oldest event is dropped;
- =dropped_count= records overflow;
- a plugin may hold at most 16 subscriptions;
- close a subscription with =subscription.close()=;
- runtime cleanup closes remaining plugin subscriptions automatically.

The event stream is provider-neutral. Do not parse backend implementation logs as a substitute for events.

** =start_worker(name, target)=

Starts a managed worker. =target(stop_event)= receives a =threading.Event= that is set during cleanup.

Managed workers are limited by =[plugins].max_managed_workers=. Runtime cleanup signals and joins them within the lifecycle deadline.

If you create resources outside =start_worker()=, =stop()= still needs to release them promptly.

* Threading rules

Runtime publishers never call plugin or UI callbacks directly. Subscription queues are the boundary.

Plugin workers may call =runtime.dispatch(...)= from any thread. =RuntimeHost= executes accepted commands on its dedicated asyncio thread.

A plugin worker must not touch Qt widgets. UI updates flow through runtime events and =QtRuntimeBridge=. Qt is already creative enough about thread affinity without external plugins helping.

* Things plugins must not reach into

Do not retain/use concrete references to:

- =RuntimeHost= internals;
- concrete agent backends;
- =AgentManager= internals;
- Qt widgets/controllers;
- microphone/VAD/speech provider objects;
- =PrologEngine= internals;
- Pet widgets/state internals.

Do not create a parallel:

- runtime;
- event bus;
- speech pipeline;
- timer scheduler;
- notification system;
- UI-control path.

If the facade cannot express a legitimate application-level operation, extend the runtime contract rather than tunneling around it from a plugin.

* Configuration

Generic resource bounds:

#+begin_src toml
[plugins]
lifecycle_timeout = 5.0
event_queue_size = 256
max_managed_workers = 8
#+end_src

Plugin settings use the metadata name:

#+begin_src toml
[plugins.event-observer]
enabled = true
#+end_src

Zara copies only that private table into the facade. Generic diagnostics do not expose the plugin's private settings.

Full config context: [[file:../docs/configuration.org][configuration.org]] and [[file:../docs/config/main.org][config/main.org]].

* Failure isolation

=RuntimeHost.plugin_diagnostics()= reports bounded =PluginDiagnostic= records containing only basic identity/type/state and sanitized error text.

Lifecycle states distinguish:

- =installed=
- =loaded=
- =running=
- =stopped=
- =failed=
- =incompatible=

Tool-only legacy modules normally report =loaded= because there is no service lifecycle to run.

An incompatible API version is not started. Import, factory, tool, startup, worker, and shutdown failures are isolated to that plugin and produce a non-fatal runtime error event. Error text is bounded/single-line and does not include plugin configuration.

* Shutdown order

On =RuntimeHost= shutdown, started services are stopped in reverse discovery order. Zara then closes their subscriptions, signals/joins managed workers, and unregisters their tools.

Repeated host start/shutdown calls are designed not to duplicate lifecycle calls.

* A practical checklist

Before considering a service plugin done:

1. Import has no side effects.
2. =metadata.api_version= is supported.
3. =start()= returns promptly.
4. All subscriptions are bounded.
5. Long-running work uses managed workers or is otherwise explicitly cleaned up.
6. No Qt/backend/Prolog internals leak through the plugin boundary.
7. Optional runtime commands handle =UnsupportedRuntimeCommand=.
8. Tool names do not collide.
9. Errors do not contain private configuration/credentials.
10. Stop/restart does not leave workers, processes, sockets, or tools behind.
