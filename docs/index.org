* Read this before spelunking

Zara has enough moving parts now that “open whatever file sounds relevant” stopped being a documentation strategy.

This page is the map.

The important distinction throughout the docs is *shipped behavior on =master=* versus *research, plans, and roadmap work*. If a design document describes something clever but [[file:features.org][features.org]] says it is not wired yet, it is not wired yet. Architecture prose does not get voting rights over the executable.

** Literate configuration examples

The config docs are meant to be read, copied, and modified without opening =zara/config.py= in one window and guessing in another.

- [[file:config/main.org][config/main.org]] — annotated =config.toml=.
- [[file:config/prolog.org][config/prolog.org]] — annotated user =config.pl= / symbolic overrides.
- [[file:config/mcp.org][config/mcp.org]] — annotated =mcp.toml= and MCP server examples.

They are documentation, not a second source of defaults. Canonical Python defaults still live in =zara/config.py=; canonical Prolog defaults live in =kb/config.pl=; MCP merge/validation rules live in =zara/mcp/config.py=.

** Research and design history

[[file:desktop-copilot-design.md][desktop-copilot-design.md]] is valuable because it records why the desktop architecture was chosen. It is not the current-feature checklist. Some of it landed. Some of it did not. Some of it has been superseded by the runtime that now exists.

That pattern applies to research PRs too. A draft PR can explain future architecture without becoming product documentation by osmosis.

* Status language

The docs use a small vocabulary on purpose:

- *Shipped* — present on =master= and expected to be covered by the repository's regression gate.
- *Optional* — shipped, but disabled or unused until configured.
- *Experimental* — present on =master= but still rough or deliberately narrow.
- *Unsupported* — code may be portable, but this project does not promise the platform/install path.
- *Not implemented* — visible placeholder, CLI flag, interface hook, or design concept with no working current path.
- *Roadmap* — tracked future work, normally in [[https://github.com/lost-rob0t/zara/issues/1][issue #1]].

Please do not “upgrade” *Not implemented* to *Experimental* because a class name exists. Humans have suffered enough from optimistic README files.

* Keeping this sane

When a feature changes, update the page that owns the explanation and then update links/status in [[file:features.org][features.org]] if the user-visible capability changed. When a new configuration family appears, add it to [[file:configuration.org][configuration.org]] and the relevant literate config. When a deterministic verb gains or loses a real effect, update [[file:commands.org][commands.org]] rather than leaving a parser synonym to impersonate a feature. When a design graduates into working code, move the claim out of the design document and into current docs.

The contributor rules in [[file:../AGENTS.md][AGENTS.md]] are the final maintenance checklist.
