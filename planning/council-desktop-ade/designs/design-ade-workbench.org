#+TITLE: ADE Workbench — an IDE-grade split workspace for Zara Desktop
#+FILETAGS: :design:council:desktop:prolog:ade:
#+DATE: 2026-11-26

* 1. Vision

The ADE Workbench turns Zara Desktop into a JetBrains-class split workspace: the
canonical copilot conversation lives on the left, a persistent, always-live
Prolog workbench fills the right, and a slim activity ribbon spans the top
reporting engine/daemon state at a glance. The feel is *purposeful density* —
crisp 1px-separated panels, semantic theme tokens, monospace typography for
everything Prolog — a tool for people who think in clauses, not a toy chat
with a debug drawer. The Prolog environment is never hidden: facts, queries,
results, and actor state are first-class citizens of the main window, one
keyboard focus away (Ctrl+K), always bound to the one authoritative engine
running inside zara-server.

  Qt thread; completions arrive as signals via queued delivery

- A safe Prolog toolchain already ships: =PrologSourceRepository= (approved

  (theme.py:142-160). No raw hex outside =theme.py=.

  and all ribbon labels =Hack Nerd Font Mono= 13px (editor/results) and 11px/700

  theme.py:647-656; copilot.py:69). Workbench chrome uses 8px radii — visibly

  =Ctrl+P= quick-open predicate (filters KB tree). All via =QShortcut= on the
  canonical window.

* 4. Prolog ADE architecture

** Process / thread model

- *One engine, one process*: all Prolog execution happens in the zara-server
  runtime process behind =PrologEngine= (prolog_engine.py:327). The desktop
  process never imports pyswip. Every read goes through the existing command
  path: =Workbench → client.submit(RunPrologQuery) → RuntimeHost → backend
  → engine.query_all= (controller.py:58-60; host.py:708-717;
  backend.py:407-417).
- *Qt thread only renders*: submissions happen off-thread via
  =ZaraClient.submit=; results arrive as =command_completed= /
  =command_failed= signals (qt_bridge.py:64-82). This is the same discipline
  the settings console is tested for (t/test_desktop_settings_window.py:204-231).

** New module layout (all UI-free logic kept pure and testable)

- =modules/desktop_ade.pl= — Prolog-owned *flat catalog projections* mirroring the
  proven =frame_head_row/frame_slot_row= pattern (prolog_engine.py:517-538):
  =desktop_ade:fact_group(Group)=, =fact_pred(Group, Functor, Arity, Count)=,
  =fact_row(Functor, Arity, Idx, TermAtom)=, plus =desktop_ade:intent_index= over
  =kb_intents:verb_intent/3=. Prolog logic stays in Prolog (AGENTS.md invariant).
- =zara/desktop/ade.py= — pure model: =QueryFence= (generation counter, stale
  detection), =CatalogModel= (functor→clause tree rows), =ResultTable= (solutions
  → rows, bounded formatting). Zero Qt imports; unit-testable like
  =zara/desktop/state.py=.
- =zara/desktop/windows/workbench.py= — =AdeWorkbenchPanels= widget + =ActivityRibbon=
  widget; embeds =PrologHighlighter= from prolog_studio.py for the editor.

** Fact → UI projection (KB explorer)

- Refresh = submit =RunPrologQuery("desktop_ade:fact_pred(G,F,A,N)", 100)=.
  Expanding a predicate submits
  =desktop_ade:fact_row(F,A,Idx,Term)= (≤100 rows). Rows render as a
  =QTreeWidget=; counts come from Prolog, never from file reading — files are
  not truth, the engine is.
- Refresh triggers: manual (F5 on tree), after =prolog_reload= success, and after
  =RuntimeStarted= events. No polling loops; the event bus is the heartbeat
  (qt_bridge.py:50-54 drains what the daemon emits).

** Query lifecycle (submit / fence / cancel / render)

1. *Submit*: goal validated client-side to mirror =RunPrologQuery.__post_init__=
   bounds (commands.py:123-129); generation =N= is captured; editor locks, ribbon
   shows =query N running=; entry inserted into the 20-entry history list
   (mirroring settings.py:909-915 and =query_history= limit 20,
   desktop_prolog_ide.pl:23).
2. *Fence*: =QueryFence= stores =N=. A receipt finishing when =current ≠ N= is
   discarded and its history row is annotated "superseded" — the exact contract
   already proven in settings (settings.py:935-938) and its test
   (t/test_desktop_settings_window.py:234-249).
3. *Cancel*: =Esc= bumps generation and marks the row cancelled ("late results
   will be discarded", settings.py:927-933).
4. *Render*: solutions → monospace table; variables become columns; ≤ 50 rows
   requested (ui_requested_solutions 50, desktop_prolog_ide.pl:22) out of the ≤
   100 allowed (commands.py:128); total rendered text capped at 64000 chars
   (rendered_output_chars, desktop_prolog_ide.pl:24). A result banner records
   generation, goal, and solution count (e.g. =gen 7 · 2 solutions=, matching the
   existing status text contract, t/test_desktop_settings_window.py:229).

** Intents & tasks surfaces

- *Intents*: KB explorer has a first-class =kb_intents= group projected from
  =verb_intent/3= (kb/intents.pl:14) plus a live "resolve" action that submits
  =intent_resolver:resolve(Text, State, Intent, Args)= — the exact goal
  =PrologEngine.resolve_intent= runs (prolog_engine.py:469-484) — so you can
  watch routing decisions happen in the real engine.
- *Tasks & actors (phase 1, zero new protocol)*: the panel maintains a bounded
  live model from the runtime event stream the desktop already receives:
  TurnStarted/TurnCancelled/ToolStarted/ToolWaitingForUser/ToolCompleted/
  AgentFailed (events enumerated by the reducer, zara/desktop/state.py:45-97).
  Rows show turn/tool ids with =TaskStatus=-compatible labels
  (zara/tasks/store.py:27-36). Read-only by construction.
- *Durable task list (phase 2)*: a read-only =tasks.list= protocol message mapped
  to =Capability.RUNTIME_STATUS= (the existing read-only capability,
  security_gateway.py:144-145), returning a frozen snapshot from
  =zara/tasks/store.py=. No transitions are ever initiated from the UI
  (AGENTS.md long-horizon rule).

* 5. Invariants & security

- =single_engine_authority=: the workbench holds no engine, no pyswip import, no
  file-as-truth. Every fact, query, and intent lookup is a =RunPrologQuery=
  against the manager's one engine (backend.py:414-417). The KB tree shows what
  the engine answers, not what files contain.
- =no_qt_thread_prolog=: identical to the shipped pattern — submissions happen
  through =ZaraClient.submit= (worker-owned), completions arrive as Qt signals
  (qt_bridge.py:69-82). A new test asserts the query callable never runs on the
  Qt thread (mirrors t/test_desktop_settings_window.py:204-231).
- =admin_gated_remote_query=: the workbench adds no new query transport; it
  reuses =prolog.query= which the gateway maps to =Capability.DAEMON_ADMIN=
  (security_gateway.py:157-158). The phase-2 =tasks.list= is read-only status,
  mapped to =RUNTIME_STATUS= — it never becomes a query path.
- =late_query_results_are_fenced=: generation fence in =QueryFence=, one fence
  per workbench surface, cancel discards late receipts, stale receipts are
  visibly annotated. Same contract as settings, enforced by new tests.
- Themes project from =ZaraTheme.kt=: the workbench introduces no new colors;
  ribbon/panels/table consume only the existing 15 semantic roles
  (theme.py:142-160); the =PrologHighlighter= already re-themes itself per theme
  (prolog_studio.py:372-393).
- No new non-Nix dependencies: everything is PySide6 widgets + the existing
  swipl/pyswip stack. The IDE-grade look is achieved with stylesheets,
  =QSplitter=, =QTreeWidget=, and =QPlainTextEdit= — the same primitives the repo
  already ships.
- Prolog logic stays in Prolog: catalog projections and the intent index live in
  =modules/desktop_ade.pl=; Python only renders rows.

* 6. Failure & recovery

- *Engine crash / daemon loss*: =RuntimeError=/=RuntimeStopped= events reduce to
  DISCONNECTED/ERROR (state.py:49-65); the ribbon lamp goes danger, panels show
  "Engine unavailable" and disable submission; =RestartRuntime= via the existing
  controller path (controller.py:246-260). On =RuntimeStarted=, panels clear and
  re-fetch the catalog; open queries are fenced out by generation bump.
- *Stale results*: generation fence as above; late receipts never touch the
  table (tested).
- *Barge-in*: running a new goal while one is in flight bumps the generation and
  marks the in-flight row "superseded" — the UI never queues unbounded queries;
  at most one outstanding workbench query at a time (the engine lock serializes
  anyway, prolog_engine.py:335).
- *Long queries*: cancel is always reachable (=Esc=, ribbon spinner click);
  solutions bounded at 50 requested/100 max; the runtime already converts query
  failures into =RuntimeError= events instead of hangs (host.py:726-737). A
  runaway goal's worst case is a blocked engine — documented risk with
  =call_with_time_limit= as a future server-side hardening (out of scope here).
- *Restart*: COMPACT/EXPANDED/WORKBENCH geometry, splitter sizes, and theme are
  =QSettings=-persisted using the existing geometry machinery (copilot.py:216-225);
  conversation state is untouched by presentation changes (copilot.py:137-146).

* 8. Acceptance criteria

1. =CopilotWindow= gains WORKBENCH presentation; switching COMPACT↔EXPANDED↔WORKBENCH
   preserves conversation id, message widget identities, and composer draft with
   zero runtime commands issued (extends the single-renderer test family).
2. WORKBENCH geometry persists under =desktop/copilot/workbench-geometry= and is
   restored independently of the other two keys.
3. Query editor: valid goal → ≤50-row fenced result table with =gen N · M solutions=
   banner; goal >4096 bytes or max_solutions out of 1..100 is rejected locally
   with a message (mirrors commands.py:123-129).
4. Cancel discards late receipts (status "Cancelled · late results will be
   discarded"); a second run while one is in flight marks the first "superseded"
   and never renders its results.
5. History holds the last 20 goals, newest first, selectable.
6. KB explorer renders groups/predicates/clause-counts answered by
   =desktop_ade:fact_pred/4= and rows via =desktop_ade:fact_row/4=; no desktop
   module reads =kb/= files as truth.
7. Intent resolve action returns the engine's =Intent/Args= for a typed phrase and
   renders them as a one-row table.
8. Ribbon reflects every =DesktopRuntimeState= with lamp color variants
   (primary/active/danger, theme.py:600-624) and shows daemon endpoint + last
   query generation.
9. All colors in new widgets come from =THEME_REGISTRY= roles; new stylesheet
   rules live in =desktop_stylesheet= only.
10. The query callable used by the workbench is never invoked on the Qt main
    thread (test asserts thread identity).
11. Existing gates pass unchanged: t/test_adaptive_copilot.py,
    t/test_desktop_theme.py, t/test_copilot_screenshot_fixtures.py,
    t/test_desktop_mobile_parity.py, t/test_desktop_settings_window.py.

* 10. Rejected alternatives

1. *Detached ADE window* (separate top-level Prolog console paired with the chat
   window). Loses: single-window keyboard flow, duplicates geometry/status
   plumbing, and tempts a second conversation renderer. The one-renderer
   invariant (copilot.py:39-40, t/test_adaptive_copilot.py:93-103) exists
   precisely because duplicated surfaces drift. A dock inside the canonical
   window keeps one truth and one focus order.
2. *In-process playground engine* (desktop imports pyswip for instant queries).
   Blatantly forks engine authority and drags SWI onto the GUI process; both
   named invariants fail (desktop_prolog_ide.pl:10-13). Latency is not worth a
   second truth; the daemon IPC round-trip is already sub-second for bounded
   goals.
3. *WebEngine/HTML IDE* (Monaco-style editor, DOM tables). New non-Nix dependency
   class, violates the prefer-Qt-native rule, and the repo already proves
   QPlainTextEdit + QSyntaxHighlighter + QTextBrowser reach the target quality
   (prolog_studio.py:355-405, chat_widgets.py:31-57). Nothing in the lens needs
   a browser.

* 11. Risks

1. *Engine lock contention* — a heavy catalog query serializes with live intent
   resolution (the whole point of =_runtime_lock=, prolog_engine.py:330-335).
   Mitigation: cheap flat row projections, max_solutions=100, manual refresh
   only, one outstanding workbench query.
2. *Result-table cost / layout jank* — wide multi-variable bindings can explode.
   Mitigation: ≤50 rows, per-cell truncation with ellipsis, 64000-char render
   cap (desktop_prolog_ide.pl:22,24), virtualized =QTreeWidget= rows.
3. *Fixture-matrix churn* — adding workbench states changes the "closed" fixture
   manifest and screenshot budget. Mitigation: grow the set in the same change
   that adds panels; keep rendering offscreen, theme-locked to outrun, and
   sha256-evidenced exactly like ui_fixtures.py:237-288 so the evidence transport
   stays valid.
