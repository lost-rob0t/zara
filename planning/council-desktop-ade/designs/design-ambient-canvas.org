#+title: Ambient Canvas — the desktop as a live projection of the Prolog engine
#+author: Design council / lens: Ambient Canvas
#+status: draft

* 1. Vision

Kill the chat transcript. Zara Desktop becomes an *ambient canvas*: an
edge-to-edge, near-chromeless vertical surface where every thing the engine
does — a fact asserted, a goal answered, a tool run, a task transition, an
assistant sentence — materializes as a first-class animated card, projected
from real Prolog state. The knowledge base *is* the UI state store; Qt
widgets are disposable projections of engine facts, rebuilt or fenced on
generation change. The only permanent chrome is one floating command bar
(Raycast-class): type a sentence and it becomes an agent turn; type ~?-
color(X).~ and it becomes a live query card. The feel is Arc-browser calm
over engine truth: deep outrun ground, soft elevation shadows, one accent
that means "the engine is answering you", motion that exists only to
explain state change. The Prolog ADE is not a settings tab bolted on the
side — it is the entire window.

** Fact→UI projection (the mirror)

New Prolog, logic stays in Prolog per repo rules:

- =kb/desktop_canvas_facts.pl= — fact vocabulary:
  #+begin_src prolog
  canvas_card(Id, kind, Attrs).      % Attrs: bounded ground terms, ≤4 KiB
  canvas_order(Seq, Id).
  canvas_generation(G).              % bumped by every mirror mutation
  canvas_surface_invariant(single_engine_authority).
  canvas_surface_invariant(no_qt_thread_prolog).
  canvas_surface_invariant(late_query_results_are_fenced).
  canvas_surface_invariant(admin_gated_remote_query).
  #+end_src
- =modules/desktop_canvas.pl= — the logic:
  - =mirror_event(+EventTerm)= — pure translation of one runtime event
    (intent/tool/task/assistant lifecycle, mirror-loss) into
    assert/retract of =canvas_card/=canvas_order= plus a =canvas_generation=
    bump. Mirrors the reducer discipline of state.py:39-99 and the CAS
    fencing doctrine of symbolic_projection.py:481-546.
  - =classify_input(+Text, -Route)= — =query/1= for the =?- = prefix,
    =palette/1= for =/= verbs, =turn/1= otherwise. The command bar routes by
    asking the engine, not by Python string logic.
  - =canvas_delta(+SinceGen, -Gen, -Cards)= — ordered changed-cards projection,
    bounded =MaxSolutions=; =visible_cards/2= for full rebuilds.
  - PlUnit tests embedded; loaded from =main.pl=.
- *Who feeds the mirror*: a host-side seam (runtime process, never desktop,
  never Qt) — after the host publishes each event (host.py:730-736,745-751),
  it also translates the event to the portable term and calls
  =engine.query_once("desktop_canvas:mirror_event(...)")= on its own worker
  context, wrapped so mirror failure is logged and degrades, never breaks a
  turn. This keeps *one* engine (=single_engine_authority=: the mirror facts
  live inside the authoritative engine; nothing forks a second SWI runtime,
  which =prolog_engine.py:328-334= makes impossible anyway).
- *The Qt rebuild rule*: =CanvasWindow= renders =visible_cards= /
  =canvas_delta= results only. If =Gen= is unchanged → patch widgets in place
  (the quick.py:336-349 diff pattern, now keyed on engine generation instead
  of message-id tuples). If =Gen= moved → rebuild the affected window of
  cards. Widgets hold no state that outlives a generation.

** Query lifecycle (submit / fence / cancel / render)

1. *Submit*: bar text → =classify_input= → =RunPrologQuery(goal, 50)=
   (=ui_requested_solutions= 50 per desktop_prolog_ide.pl:22; wire bounds
   enforced at commands.py:119-129). A query =QueryCard= is born in =running=
   state; the bar keeps its draft history like settings does
   (settings.py:909-915).
2. *Fence*: the canvas keeps a local monotonic =_submit_generation=, bumped on
   every new submit and on cancel; completions arrive with
   =request_id= + generation and render only if current — the
   settings.py:896-937 mechanism, per-card.
3. *Engine side*: host dispatches (host.py:708-717) → backend
   =engine.query_all= (backend.py:407-417) under the process-wide lock;
   =PrologQueryCompleted(success, summary)= (events.py:196-199) feeds the
   mirror so other surfaces see the pulse.
4. *Cancel*: no wire cancel exists for queries (commands.py has none), so
   cancel = generation bump + "cancelled · late result discarded" state —
   the exact semantics already tested at t/test_desktop_settings_window.py:234-249.
   Render caps per card: 50 solutions, 2,000 chars/solution, 64,000 chars/card
   (settings.py:950-959 limits, reused).
5. *Render*: =QueryCard= gets goal, solutions table, =gen N= badge, duration,
   Rerun (re-submits the same goal through the same fence).

** KB browsing, intents, tasks

- *KB pulse*: managed-fact writes (prolog_studio.py add/update/delete paths,
  settings.py:1051-1134) emit events the mirror turns into =FactCard=s;
  a =/kb= palette verb queries a bounded overview goal
  (=desktop_canvas:kb_overview(-Entries)= over =current_predicate/1= counts)
  rendered as a query card. Deep editing stays in the settings Prolog IDE
  (settings.py:609-779) — the canvas links to it, it does not duplicate it.
- *Intents*: =IntentResolved= cards show intent, resolver provenance, and
  arguments (events.py:190-194 carries all three).
- *Tasks*: =TaskCard= projects the six task events (events.py:303-330);
  =TaskWaitingApproval= renders the approve affordance inline, wired to
  =ApproveTool=/=RejectTool= (commands.py:90-105) through the same bridge.

* 5. Invariants & security

- =single_engine_authority= — one SWI runtime exists per process
  (prolog_engine.py:328-335 makes a second one impossible anyway); the mirror
  lives *inside* that engine; the desktop constructs no engine and holds no
  render state of its own beyond disposable widgets. Precedence on degraded
  mirror: durable ledger (ConversationService/SQLite) is the rebuild source —
  the same "projection, not a second store" doctrine the codebase already
  states at symbolic_projection.py:1-9. New KB facts assert the invariant for
  the canvas surface explicitly.
- =no_qt_thread_prolog= — every goal travels =bridge.submit → host → backend=
  on non-Qt threads; results return as signals. Gated by a new test asserting
  the canvas query callable never runs on =QApplication.instance()=.thread.
- =admin_gated_remote_query= — the canvas introduces *no new wire type*; all
  remote goals ride =prolog.query=, whose capability is =DAEMON_ADMIN=
  (t/test_daemon_security_policy.py:12, codec at protocol_runtime.py:146-159).
  A local desktop principal's queries go through the same command path as the
  settings console today (controller.py:55-62).
- =late_query_results_are_fenced= — dual fences: engine =canvas_generation=
  for projections, local submit generation for command-bar queries; stale
  deltas and late receipts are dropped without rendering (settings.py:935-937
  semantics, symbolic_projection.py CAS doctrine).
- *Themes* — desktop projects =ZaraTheme.kt= only; no new tokens, no new
  themes; parity tests keep passing untouched.
- *No new dependencies* — cards, shadows, and motion are QtWidgets/QtGui only
  (=QGraphicsDropShadowEffect=, =QPropertyAnimation=). No WebEngine — the code
  already avoids it deliberately (chat_widgets.py:137).
- *Prolog stays in Prolog* — event→fact translation, input routing, delta
  projection, kb overview: all =modules/desktop_canvas.pl= predicates; Python
  marshals terms and builds widgets.
- *Secrecy/abuse bounds* — card payloads bounded (4 KiB attrs, 64000-char
  render cap, settings.py:957 precedent); no transcript text in structured
  latency or spine telemetry (AGENTS.md logging rule).

* 6. Failure & recovery

- *Engine crash / error*: =RuntimeError/AgentFailed/...= → state ERROR
  (state.py:55-65) → spine =danger= + a system card; command bar stays
  usable for =?- = retries once the runtime returns.
- *Restart*: =RestartRuntime= (controller.py:246-260) → mirror generations
  reset; canvas re-projects =visible_cards= from the fresh engine and replays
  conversation context from the durable ledger into the mirror (bounded
  replay, newest N cards) — restart recovery is a projection rebuild, not a
  UI migration.
- *Stale results*: late query receipts and stale deltas are fenced per §4;
  the card shows the fence outcome instead of silently vanishing (matches
  the "Cancelled · late results will be discarded" UX already shipped at
  settings.py:933).
- *Barge-in*: =TurnCancelled= (events.py:54) collapses the streaming reply
  card to cancelled state (status text exists: chat_widgets.py:357);
  approval cards time out with the turn.
- *Long queries*: cancel is always available; the mirror poll coalesces so a
  stuck delta query cannot wedge the canvas (single in-flight poll; skip
  ticks until it returns).
- *Mirror loss / degraded mode*: mirror_event failures are swallowed by the
  host seam and mirrored as one "engine mirror unavailable — projecting from
  ledger" watermark card; the canvas then renders from a
  ConversationService snapshot until generations re-sync. Chat never breaks
  because the ADE layer did.
- *Disconnect*: =DISCONNECTED= (state.py:51-54) freezes motion, keeps drafts;
  reconnect re-syncs via full =visible_cards= rebuild.

* 8. Acceptance criteria

1. With =[desktop].canvas=true=, typing a sentence in the bar submits
   =SubmitTurn= and typing =?- parent_child(X,Y).= submits =RunPrologQuery=;
   the route decision comes from =desktop_canvas:classify_input/2= (Prolog
   test), not Python string matching.
2. A canvas rendered after a generation bump is byte-identical (widget
   identity for unchanged cards, rebuilt for changed) to a canvas built from
   =visible_cards= at that generation — projection determinism test.
3. Cancelling a running query guarantees a late =PrologQueryReceipt= with
   distinct solutions never renders (settings-cancel semantics, per-card).
4. Every visible pixel color originates from =THEME_REGISTRY[theme].colors=
   roles; zero literal hex in canvas widget code.
5. Motion-off mode renders a complete, readable canvas and is a fixture state.
6. With the mirror disabled at runtime, the canvas shows the degraded
   watermark and still renders ledger-backed cards; turns still flow.
7. A query returning >64,000 rendered chars truncates with the documented
   suffix and never blocks the GUI thread >16ms per tick.
8. Approval-required tool cards expose Approve/Reject that submit
   =ApproveTool=/=RejectTool= with the card's =tool_run_id=.
9. Offscreen fixture set (≥8 states incl. streaming, tool-approval,
   query-solutions, error, motion-off, disconnected) renders deterministic

* 10. Rejected alternatives

1. *Web canvas (Electron/Tauri/QtWebEngine) for Raycast-class polish.*
   Loses: violates the Qt-native/no-new-deps invariant; the repo already
   avoids WebEngine on principle (chat_widgets.py:137); the Kotlin→Python
   token parity machinery (test_desktop_mobile_parity.py) would need a third
   consumer; offscreen determinism (ui_fixtures) is much harder. The same
   polish is reachable with palette + shadows + motion in QtWidgets.
2. *Refine the transcript instead (better bubbles, richer activity rows).*
   Loses the lens: bubbles structurally erase engine life — tool messages
   with bare status words render *no content* (chat_widgets.py:243-251), and
   there is no place for a fact, a goal, or a task to be first-class. Polish
   on a transcript cannot become an ADE; the ADE is a different dataflow
   (engine generations → widgets), not a different stylesheet.
3. *Classic dockable IDE shell (QDockWidget panels: KB tree, console,
   inspector).* Reads "IDE" but fails "simple + modern": docks are permanent
   chrome, the opposite of minimal; it would also duplicate the settings
   Prolog IDE instead of absorbing it. The command bar + overlay palette
   delivers the same capabilities with zero permanent panels.

* 11. Risks

1. *Lock contention between canvas polls and turn processing.*
   =PrologEngine._runtime_lock= is process-wide (prolog_engine.py:333-335);
   careless polling could delay turns. Mitigation: single coalesced in-flight
   =canvas_delta= poll at 150–250ms with bounded =MaxSolutions=, poll paused
   while =THINKING= bursts are active, and a latency metric through the
   existing JSONL sink (host.py:760-777) with a budget assertion in tests.
2. *Widget/perf blow-up on long sessions with animated cards.*
   Mitigation: render-window virtualization (only ±N cards around the
   viewport materialize as widgets, like =_MAX_VISIBLE_MESSAGES= at
   quick.py:29 but windowed), motion only on birth, shadow effects limited to
   focused card + command bar, and a density fixture (≥200 cards) in the
   screenshot gate.
3. *Screenshot-fixture churn from shadows/motion.*
   Mitigation: fixtures default motion-off and capture with
   =QT_QPA_PLATFORM=offscreen= (t/test_adaptive_copilot.py:6 pattern); a
   single dedicated motion fixture; sha256 manifest + full Qt-state restore
   copied from ui_fixtures.py:219-273; any pixel regression is reviewed as a
   deliberate design change, not noise.
