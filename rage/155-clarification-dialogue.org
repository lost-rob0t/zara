** Research conclusions
1. The clarification session is pure host state: conversation+principal-scoped, one per conversation, prompts derived deterministically from the frame's missing list (contract section 4; D2). No Prolog dynamic DB, no LLM prompt management, no global pending variable.
2. The machine consumes *typed* slot values; raw-utterance parsing for the ACTIVE requested slot is dialogue-layer parsing (deterministic, per-slot-type), distinct from verb/intent authority (D6 unharmed; #156 replaces utterance-level resolution with =resolve_frames/4=).
3. Frame ids and supersedes live in the session's envelope bookkeeping, never inside the frame (contract section 1).
4. Wake wire-up is limited to the existing pending shapes; unknown pending shapes keep the legacy string. Bare-timer frames ("set a timer" -> ask duration) are exercised at machine level; resolver-side production is #156.

* Design (decisions)

- D1 :: Two modules. =zara/runtime/frames.py=: IntentFrame v1 Python mirror - closed typed value set (text/number/duration/datetime/ref/boolean), slot origins (utterance/follow_up/context/default/correction), frame statuses (complete/missing/ambiguous/invalid/cancelled/superseded), immutable =IntentFrame= with NO frame id inside. =zara/runtime/clarification.py=: slot specs, per-slot-type deterministic value parsers, the clarification session state machine, and the coordinator registry.
- D2 :: Session lifecycle: ELICITING (missing/invalid/ambiguous - questions derived from required slots in spec order) -> READY (all required slots filled; frame status complete; short pre-execution window) -> CLOSED (terminal: executed/cancelled/expired/superseded/exhausted). Optional slots are never elicited.
- D3 :: Follow-up filling: only the ACTIVE requested slot when unambiguous. Invalid answer -> focused retry of the same slot (no state change beyond an attempt counter). Bounded: =max_attempts= (default 5) exhausts to a closed cancelled session.
- D4 :: Correction: leading deterministic markers ("actually", "make that", "make it", "change that to", "change it to", "no"/"no,") mark the follow-up as a correction. Targeting rule (deterministic, no LLM): if the active slot parses the marker-stripped text -> fill/replace the active slot with origin=correction; else try already-filled typed (non-text) slots in schema order -> replace that slot with origin=correction; else focused retry. A correction rotates the frame id and records =supersedes= (prior frame id) in the session bookkeeping - never inside the frame.
- D5 :: Cancellation: phrases {"never mind", "nevermind", "forget it", "cancel", "cancel that"} close the session with a cancelled frame; "stop"/"end" cancel the session and fall through to existing conversation-stop handling (no reply of its own).
- D6 :: Stale gating: follow-ups to a closed, cancelled, expired, capacity-replaced, or nonexistent session all return one byte-identical rejection ("That question isn't active anymore.") regardless of principal/conversation/reason - no cross-principal inference from wording or timing.
- D7 :: Ambiguity: an ambiguous open frame lists value alternatives for the active question; the follow-up must equal one alternative (case-insensitive) -> fills with origin=follow_up; otherwise focused retry. No default picking (contract section 4).
- D8 :: Registry: =ClarificationCoordinator= keyed by (principal, conversation_id); at most one open session per conversation (opening a new one supersedes the old with reason =superseded_by_new_dialogue=); =max_sessions= bound (default 8) with a uniform capacity rejection; per-value size bound (default 512 chars, oversized = invalid retry); TTL (default 120s) checked against an injectable clock; =drop_all(reason)= for restart/shutdown (typed degraded drop, never silent resume).
- D9 :: Concurrency: one lock per coordinator; transitions are atomic; a second concurrent submit cannot double-hold the dialogue - at READY, non-correction text is stale; the first completer owns the frame.
- D10 :: RuntimeHost integration (D2 of #154 design): host constructs a coordinator, exposes it, and =drop_all(reason)= on restart and shutdown. The wake path instantiates its own coordinator (the wake listener is its own runtime context until #157 unifies execution) using the same classes.
- D11 :: Wake wire-up: pending result -> open session from a template map (open -> ns(app)/open with target ref slot; text -> ns(message)/text with contact ref + message text slots; python(schedule_todo) -> ns(skill)/schedule_todo with task text slot; timer.set template exists for machine tests) and answer with the deterministic question; every command utterance first checks the session when the text is not command-like; completion executes via the existing =execute_intent=/=python_skills.execute= paths and then closes the session.
- D12 :: No new latency-trace schema fields; wake records =route="clarification"= / =route="clarification_stale"= using the existing route_selected event shape. No transcript text in traces.

* Threat / failure analysis
- Slot-text injection :: dialogue-layer values are typed inert values (text/ref); adapters receive plain surface strings; never executed (contract section 6; design invariants).
- Cross-principal leakage :: sessions keyed by (principal, conversation); uniform rejection strings carry no principal/session/counter data.
- Oversized/malformed input :: value size bound + per-type validation fail closed into focused retry.
- Flood :: max_sessions bound + max_attempts bound + TTL bound; capacity rejection is uniform and does not evict other principals' sessions.
- Restart :: =drop_all= on restart/shutdown; late follow-ups get the uniform stale rejection (never silently resumed - #154 design threat row).
- Double-hold race :: coordinator lock + READY-state stale rule; two concurrent submits cannot both complete the same frame.
- Legacy drift :: unknown pending shapes keep the legacy prompt; no behavior fork for intents without templates.

* Adversarial review (counterexamples)
- "hello there" after "text sarah -> ask message" with markers ("actually hello there") -> marker-stripped text fills the ACTIVE message slot with origin=correction; contact untouched. Deterministic choice of the active question over a filled text slot; resolver-driven explicit =submit_correction(slot, value)= remains available for #156 where re-resolution knows the slot. Accepted residual ambiguity, documented here.
- "never mind" mid-elicitation then "twenty minutes" -> session closed; "twenty minutes" is not command-like, no session -> uniform stale rejection; not executed, not consumed as slot fill. Matches the mandatory example.
- Concurrent A/B principals with identical frame ids/phrases -> disjoint registry keys; byte-identical rejection strings asserted in tests.
- Two conversations, one principal -> per-conversation sessions cannot steal answers.
- Timeout vs fill race -> clock is injectable; expiry check happens before any fill; an expired session is closed cancelled(timeout) and the fill is stale. Virtual clock in tests; no sleeps.
- Cancellation racing slot fill -> lock serializes; whichever transition lands first wins; the loser observes CLOSED (stale) - tested.
- Oversized answer -> size-bounded parser -> focused retry; nothing stored.
- Missing template for a pending shape -> legacy behavior preserved (bounded migration).
- READY-window correction after execution already consumed the frame -> wake closes the session before returning; late correction is stale (uniform). Machine-level callers that hold READY can still correct (covered by test).
