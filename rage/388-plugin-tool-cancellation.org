** Acceptance carried from issue
- A running service-plugin tool can observe canonical Zara turn/tool cancellation.
- Cancellation is scoped to the exact invocation and cannot be retargeted by model/tool arguments.
- Cancellation composes with existing approval and plugin unload lifecycle.
- Cancelled execution is distinguishable from timeout/failure.
- Deterministic tests can inject cancellation without network or GUI dependencies.

** Research
- =create_tools_node= remains the one canonical LangGraph execution boundary for registered =BaseTool= instances and already owns =ToolCancelled= publication on turn cancellation.
- =PluginManager= registers service-plugin =BaseTool= objects into the same =ToolRegistry= used by ordinary tools. A plugin-only execution manager, process-id registry or cancel command would fork the control plane.
- =PluginRuntime= owns lifecycle workers/subscriptions, not individual tool calls. Existing =test_cancellation_after_tool_start_emits_tool_terminal= proves only the external terminal event; a synchronous/subprocess-style plugin tool still cannot observe cancellation and release owned resources.
- LangChain service tools already carry their canonical name/schema/metadata on the =BaseTool=. A narrow wrapper can add invocation context without widening RuntimeHost/backend signatures or changing approval identity.

** Final design
*** Selected architecture
- Service-plugin =BaseTool= objects are wrapped exactly once by =PluginManager= immediately before the existing canonical =ToolRegistry= registration. The wrapper preserves tool name, schema, metadata and registration/unload identity, so approval and execution still flow through =ToolRegistry -> ToolNode= with no second manager.
- Each wrapper invocation creates one Core-owned =threading.Event= and exposes only a read-only =ToolCancellation= view through =current_tool_cancellation()=. Cancellation state is carried by =ContextVar= so LangChain synchronous executor work sees the same invocation-local token.
- The original tool runs in a child task shielded from immediate parent cancellation. When the canonical turn/task is cancelled, Core sets the cooperative token first, cancels the child task, waits for task cancellation cleanup, then re-raises. =create_tools_node= therefore remains the authority that emits the existing =ToolCancelled(reason="turn cancelled")= terminal event.
- Async tools continue to receive =CancelledError=. Synchronous tools can poll =cancelled= or =wait(timeout)= and terminate subprocess/provider work cooperatively.

*** Rejected alternatives
- Plugin-specific cancel command / process-id registry: second control plane plus retargetable identifiers.
- User/model-visible =cancel_token= tool argument: authorization/lifecycle state would become model-controlled.
- Global mutable cancellation flag: concurrent calls could cancel each other.
- Only catching =CancelledError= inside plugin code: synchronous executor tools cannot rely on receiving asyncio cancellation.
- Widen RuntimeHost/backend signatures solely for plugin cancellation metadata: unnecessary duplication of the existing tool execution path.

*** Invariants / adversarial checks
- One token per invocation; concurrent tools do not share cancellation state.
- Plugins can inspect/wait only; they cannot signal or retarget another token.
- Approval occurs before execution exactly as before; =zara_requires_approval= metadata remains intact on the wrapper.
- Plugin unload still unregisters the same bounded tool name and removes only plugin-owned dynamic approval state.
- Model/tool arguments cannot provide, replace, suppress or retarget the cancellation token.
- Canonical cancellation remains distinguishable from provider failure/timeout because the parent path still terminates as =CancelledError -> ToolCancelled= rather than =ToolFailed= or =ToolCompleted=.
