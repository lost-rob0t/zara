* Research / source analysis
- #196 requires =RoleManager.ROLE_ASSISTANT= eligibility, explicit user-driven onboarding, =VoiceInteractionService= / =VoiceInteractionSessionService= metadata, honest degraded state, UI-closed invocation, lifecycle cleanup, and one canonical typed runtime shared with Compose.
- #194 keeps Samsung-only side-button/device claims behind later hardware proof; this slice uses public Android contracts only.
- Existing Android =RuntimeState= already owns =AssistantRole= and =RuntimeEvent.RoleAssessed=, so role state must flow through that reducer rather than a second UI/service state machine.
- B1/B2/B3 voice work remains one authenticated ZARA/1 client with one mic/playback owner; Assistant-role work must not create a second assistant, STT, TTS, memory, or protocol runtime.
- Accepted #195 design requires role re-assessment on resume because role ownership may change outside Zara; UI-closed cross-process runtime ownership remains a separate acceptance item and is not faked by this slice.

* Design / invariants
- Android's observed =RoleManager= state is authoritative after a role request; Activity result data cannot optimistically grant the role.
- Role request is emitted only after an explicit user action and only while canonical state is =NotHeld=.
- Unavailable platforms fail closed and never claim Assistant eligibility.
- Role observations enter the existing reducer and must not mutate connection/session state.
- Voice-interaction services use =BIND_VOICE_INTERACTION= and an isolated lightweight =:voice= process surface.
- UI and diagnostics render canonical =AssistantRole= values verbatim enough to remain honest.
- Activity resume re-checks the platform role so external revocation/change is reflected promptly.
- Samsung setup guidance is bounded to the researched public picker/side-button paths and explicitly leaves hardware verification to #206.
