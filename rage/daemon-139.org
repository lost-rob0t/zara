* Contract

RAGE is not a euphemism for "code until CI stops complaining."

GitHub Issues are the work queue. Read the roadmap/epic, then consume the first open dependency-satisfied issue in declared order. One iteration works one consumed issue.

Each iteration follows this order:

1. Research deeply enough to falsify assumptions and challenge inherited designs.
2. Architecture/design from the evidence, including rejected alternatives, invariants, threat/failure analysis, acceptance criteria, and the exact gate.
3. Generate/implement the consumed issue's selected design.
4. Evaluate at the exact candidate head with the repository's complete gate.
5. If the gate passes, merge. If the attempt is architecturally invalid or the gate failure disproves the design, preserve the evidence, discard the failed implementation attempt, and begin a new RAGE iteration from research/design.

A stale CI run never authorizes a merge.

* Iteration 1 checkpoint - research complete

- Research artifact :: =rage/daemon-128-research.org=
- Research commit :: =eb036fc2ee5802e23acbcf2d8ad2cf08cb9852dd=
- Result :: inherited supervisor direction survived, but several assumptions did not.

Key findings:

1. =RuntimeHost= is already the right process-local runtime seam; the server must wrap it rather than build another assistant stack.
2. =PrologEngine= deliberately serializes access to one process-wide PySWIP/SWI runtime. Separate RuntimeHost threads are ownership containers, not Prolog/security sandboxes.
3. Current durable memory and parts of the event/plugin path are not principal-isolated. Production multi-principal operation remains gated on #130/#131.
4. Python daemon threads are abruptly abandoned at interpreter exit, so =zara-server= must explicitly shutdown and join every owned RuntimeHost before exiting.
5. Python signal handlers belong to the main thread. The server main thread owns SIGINT/SIGTERM and only uses handlers to request normal shutdown.
6. Modern service managers should supervise a foreground process. No double-fork/self-daemonization.
7. A held =flock= in an owner-private local XDG runtime directory is a stronger single-instance authority than PID-file truthiness.
8. Future ZeroMQ sockets must remain owned by the gateway thread/loop; RuntimeHost threads should communicate through ordinary commands/events, not share sockets.
