** Source analysis
LangGraph ToolNode exposes a documented async request wrapper. The wrapper receives ToolCallRequest plus the same execute(request) function that owns ToolNode validation, graph/runtime injection, error handling, and result normalization. ToolCallRequest.override(tool=...) is explicitly supported for per-invocation dynamic tool substitution.

ToolNode strips caller-supplied values for InjectedToolArg fields immediately before invoking request.tool. That is the correct anti-spoofing behavior and must remain. Therefore Core must not fight the strip stage; it must reattach its trusted value at the final invocation boundary.

** Design
- Keep ToolCancellationArg as generic InjectedToolArg so it stays absent from the model-facing tool schema.
- Keep the existing gated Core node as the only approval/current-binding authority.
- Create one Core-owned cancellation signal per exact approved invocation and overwrite any model-supplied cancellation value before entering ToolNode.
- Configure the existing ToolNode with one awrap_tool_call function.
- Wrapper accepts a cancellation value only when it is the Core ToolCancellation object already placed by the gated node.
- Wrapper substitutes only request.tool with a one-invocation delegate and invokes execute(request.override(tool=delegate)) exactly once.
- ToolNode performs its normal injected-argument stripping/validation/error policy. The delegate then reattaches the captured Core cancellation view immediately before calling the original BaseTool.ainvoke.
- On turn cancellation Core signals first, then cancels/awaits the ToolNode task; ToolCancelled(reason="turn cancelled") remains the sole terminal cancellation event.
- No direct plugin-function call, no second executor, no second approval route, no ContextVar, no shared mutable per-tool cancellation state, no Android changes.

** Adversarial properties
- Model spoof: ToolNode strips caller cancellation and the delegate overwrites with the Core value.
- Concurrent calls: cancellation lives in a per-request delegate, not a tool-global or context-global slot.
- Approval rejection/unload: existing gates return before signal creation/execution.
- Third-party BaseTool compatibility: delegate calls the registered tool's public ainvoke boundary; ToolNode remains the execution owner.
- Errors: validation/errors still traverse ToolNode because its execute(request) path is retained.
