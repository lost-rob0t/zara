* Research
** Current production gap
- =zara/server.py::_validate_ipc_endpoint= rejects every non-IPC endpoint with the stale message that auth belongs to issue #130.
- =ZaraServer._build_default_gateway= always creates =ZaraZmqGateway=.
- =zara/security_gateway.py= already implements =SecureZaraZmqGateway=: mandatory CURVE server socket, ZAP =RegistryAuthenticator=, live =SecurityRegistry= lookup, principal binding, capability authorization, quotas and bounded audit.
- =zara/security.py::SecurityRegistry= already owns enroll/revoke/rotate semantics but is memory-only.
- =zara/security.py::validate_secret_key_file= already enforces owner-only, regular, non-symlink key files.
- #130 acceptance explicitly requires long-term daemon CURVE identity, client enrollment/rotation/revocation, opt-in safe remote listening and sanitized diagnostics.

** Design pressure
Android #173 cannot prove authentication against stock =zara-server= if secure construction exists only in tests. Do not fork a second daemon or invent HTTP pairing. Reuse the existing #130 gateway/policy boundary and add the missing production state/CLI wiring.

* Design
** Scope
1. Add durable owner-private security state under an explicit directory (default XDG state/config-owned path selected by implementation, overridable for tests/operators).
2. Persist one daemon CURVE keypair and a versioned enrolled-client registry. Never serialize daemon secret into logs or CLI output.
3. Add owner-local management commands to initialize/show-public-key/enroll/revoke/list clients without opening an unauthenticated network control plane.
4. Keep local owner-private IPC as the default and existing =ZaraZmqGateway= path.
5. Permit =tcp://= only when secure state is explicitly supplied/enabled; then construct =SecureZaraZmqGateway= with the durable registry and daemon keypair.
6. Grant only an explicit bounded default Android/client capability set at enrollment; no implicit admin.
7. Security registry persistence writes atomically and validates every record by reconstructing it through the existing typed registry semantics.

** Invariants
- No TCP listener can reach ordinary =ZaraZmqGateway=.
- No secure TCP startup without a valid daemon secret + public key and readable valid registry state.
- Daemon secret file is mode 0600, regular, owner-owned and non-symlink.
- Public key may be printed; secret key never is.
- Registry device/public-key uniqueness and active/revoked state survive restart.
- Local IPC default behavior and current desktop/CLI path remain unchanged.
- Enrollment is an owner-local operator action; remote unauthenticated self-enrollment is out of scope.
- Android key Z85 form is accepted exactly as #130 already accepts it.

** TDD map
1. Production parser/server continues accepting default IPC and rejects TCP without secure configuration.
2. Security state initialization creates stable daemon CURVE keypair with private permissions and stable public key across reload.
3. Durable registry enroll -> reload -> resolve; revoke -> reload remains denied; malformed/duplicate/oversized state fails closed.
4. Owner CLI enrollment/list/revoke exposes only public/device/principal metadata and never daemon/client secrets.
5. =ZaraServer= secure TCP configuration selects =SecureZaraZmqGateway= and passes the durable registry/CurveServerConfig; IPC remains ordinary gateway.
6. A deterministic inproc/tcp secure integration fixture performs CURVE client + ZARA/1 hello for enrolled key, rejects unknown/revoked key and wrong pin.

* Iteration 2 - live authorization authority
** Reviewer finding
- Exact #331 head =83e4f4828a3c2928ae95aede3943f5d4439bb44d= creates the secure gateway from one =SecurityRegistry= loaded at daemon startup.
- =--security-enroll-key= and =--security-revoke-device= run in a separate owner CLI process and instantiate a different =PersistentSecurityState= / registry. They update =clients.json= only, so the running ZAP/gateway registry never changes.
- This violates #329's no-restart revocation/enrollment contract and leaves disk persistence and live authorization as two independent truths.
- Exact-head CI #1004 also exposed a separate deterministic persistence defect: initial =CurveServerConfig= keys are =bytes= while reloaded keys are =str=.

** RED
- Test-first commit :: =7c62117ecc55c488771b5496be84bd0b75bcb74b=.
- New oracle :: =test_owner_security_management_mutates_running_registry_without_reload= starts the secure production server with no enrolled client, invokes the normal owner security-management path after startup, requires that client to complete a real CURVE + ZARA/1 =hello.ok= on the same daemon, then revokes it and requires the existing connection's next message to receive =authentication_required= without restart.
- Source proof of RED :: current management constructs a separate state/registry and cannot mutate =ZaraServer._security_registry=, so the post-start client cannot authenticate.

** Adversarial design review
Rejected:
- filesystem polling/watchers or periodic =clients.json= reload: creates delayed/reload-based authority and contradicts the requested live-registry contract;
- restart-after-enrollment: violates #329 acceptance and makes mobile enrollment operationally brittle;
- unauthenticated remote self-enrollment: expands the attack surface and bypasses owner authority;
- model/tool-controlled raw admin requests on the remote TCP listener: capability visibility must not become enrollment authority.

Selected:
- one bounded owner-private Unix control socket owned by the same =zara-server= process and located under the mode-0700 security directory;
- Linux peer UID validation plus mode-0600 socket permissions;
- versioned, bounded JSON operations only: =enroll=, =revoke=, =list=; no arbitrary callable/shell/eval surface;
- the control handler receives the exact =SecurityRegistry= object already used by =RegistryAuthenticator= and =SecureZaraZmqGateway=, so mutations become visible immediately to ZAP and per-message authorization;
- persistence remains durable evidence/state for restart, but never becomes the live authorization mechanism;
- management CLI uses the live control endpoint whenever it exists; a stale/unreachable endpoint fails closed rather than silently editing disk underneath a running authority;
- pre-start enrollment/revocation remains available when no live control endpoint exists.

* Iteration 3 - security fuzz and chaos hardening
** Motivation
The authenticated boundary now has durable state, a live registry, a local owner control channel, CURVE/ZAP authentication and a remote protocol gateway. Deterministic happy-path tests are necessary but insufficient: malformed inputs and rare ordering/failure states must be able to fail closed without creating a second authority.

** Fuzz coverage
- =t/test_security_fuzz.py= uses deterministic seeded mutation fuzzing with no external dependency so it runs in the normal Nix/pytest gate.
- CURVE public-key mutations cover truncation, extension, embedded NUL, non-ASCII and invalid byte forms; every malformed enrollment must reject without leaving an enrolled identity behind.
- persisted =clients.json= receives randomized bounded JSON-shaped values plus malformed UTF-8 and known structural-invalid corpus entries; the accepted exception surface is =SecurityStateError=, and any accepted state must still traverse typed registry validation.
- owner-admin requests receive randomized versions/actions/values plus an unknown field that guarantees invalid shape; malformed requests must not mutate persistence or live authority.

** Chaos and fault-injection coverage
- =t/test_security_chaos.py= concurrently drives eight owner clients through live enroll/list/revoke interleavings and reconciles final durable state against the exact live =SecurityRegistry=.
- a client that disconnects after sending a truncated JSON request must not poison the admin loop; the next valid owner request must succeed.
- live-registry divergence during enrollment or revocation is deliberately injected; persistence must roll back to its prior state instead of creating split-brain authorization.
- the admin socket disappearing while the daemon lease remains held is modeled explicitly. This exposed a real gap: socket absence previously looked identical to an offline daemon and allowed a disk-only mutation.

** Chaos-derived production fix
- Offline security mutation now first proves that =ServerLease= can be acquired.
- If the daemon lease is held but the live security admin endpoint is missing, Zara fails closed with =refusing disk-only security mutation=.
- A stale/unreachable socket already failed closed; now both *present-but-broken* and *unexpectedly missing while daemon-live* paths reject disk-only authority changes.
- Read-only client listing also prefers live state and refuses a disk-only snapshot while the daemon is live but its control endpoint is unavailable, avoiding misleading operator state.

** CI policy
- Fuzz seeds are fixed and bounded in the required suite so regressions are reproducible from the failing seed.
- Chaos tests use bounded thread counts, socket deadlines and no sleeps as correctness oracles; no probabilistic pass condition is allowed.
- Larger soak/fuzz counts can be run manually by increasing the seed/case corpus, but required CI remains fast and deterministic.
