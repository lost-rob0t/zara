** Research
- Android package visibility applies to package-query APIs for targetSdk 30+, so a launcher that derives capability availability from known packages must declare only the reviewed packages it needs to inspect.
- Android's package-visibility guidance prefers direct intent launch plus explicit failure handling when availability need not be known beforehand. Zara does need availability before advertising =open_app=, so bounded manifest =<queries><package>= declarations are justified here.
- =PackageManager.getLaunchIntentForPackage= provides a front-door launch Intent for a known package and returns null when unavailable. The adapter never accepts a package name from ZARA/1; package candidates remain Android-owned constants.
- Sources :: https://developer.android.com/training/package-visibility/use-cases ; https://developer.android.com/reference/android/content/pm/PackageManager

** Design
- The server supplies a closed semantic app alias, never a package name, Intent, class, component or shell command.
- Initial reviewed aliases are bounded in Android production code and map to fixed package candidates owned by the app.
- Capability is advertised only if at least one reviewed alias resolves locally.
- Known-but-unavailable alias returns typed =unavailable=; unknown aliases and raw package-like input return =invalid_arguments=.
- Launch success is returned only after Android accepts a resolved reviewed launch Intent; no optimistic/fake success.
- Routine diagnostics do not record the requested alias or package target.
- Initial reviewed aliases are =browser= and =youtube=. ReVanced/Vanced/provider preference remains a later provider-policy slice; this transaction does not hardcode one unofficial package as semantic truth.
