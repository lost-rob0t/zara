* Iteration 1 checkpoint - research complete

- Research artifact :: =rage/daemon-130-research.org=
- Research commit :: =3f19fed3073b8edbc878a406f351046b11d80727=
- Result :: CURVE/ZAP direction survived, but ZAP-only revocation was rejected.

Decisive findings:

1. CURVE gives transport authentication/confidentiality, not Zara capability authorization.
2. ROUTER identity remains delivery metadata and cannot become principal identity.
3. PyZMQ exposes ZAP-authenticated CURVE =User-Id= on =zmq.Frame= metadata when receiving with =copy=False=.
4. PyZMQ's default successful CURVE =User-Id= is the Z85 client public key, providing a clean server-side key lookup boundary.
5. ZAP checks connection admission, so an established connection must be revalidated against Zara's key registry on every application message for immediate revocation.
6. Callback-backed CURVE auth is preferable to =CURVE_ALLOW_ANY= or certificate-directory state as the canonical authority.
7. Current #129 server already rejects TCP/non-IPC endpoints. #130 should extend that safe listener gate rather than weaken it.
8. #130 can enforce route/request/concurrent-command/malformed budgets now; provider/tool/audio quotas need later runtime message-family hooks and must not be faked.
9. Audit records must be identifier/decision only and cannot contain =turn.submit= text, payload bodies, transcripts, prompts, audio, environment dumps, or secrets.
10. #131 still owns persistence/context/memory isolation; authenticated principals in #130 are not a false claim that multi-user privacy is complete.
