** Research
- The canonical agent loop already owns cancellation. =create_tools_node= invokes each approved tool through the existing LangGraph =ToolNode= and maps =asyncio.CancelledError= to =ToolCancelled= before re-raising.
- =run_conversation_loop= owns graph/checkpointer lifetime and propagates turn cancellation; approval cancellation already raises =asyncio.CancelledError=.
- Service plugins expose ordinary LangChain =BaseTool= values through =ServicePlugin.tools()=. =PluginRuntime= intentionally has no second execution/control plane.
- Gap: a running service tool has no supported Core API for distinguishing canonical tool-task cancellation from ordinary timeout/failure while performing cooperative cleanup.

** Initial design
- Preserve the existing =ToolNode= and task cancellation path as execution authority.
- Initial RED explored a separate invocation context carrying principal/turn/tool-run identity plus an event.

** Adversarial simplification
- The exact running asyncio task is already the cancellation scope selected by Core after principal, turn, approval, and tool-run routing are complete.
- Exposing those identities again to plugin code adds coupling and a second identity-bearing surface without improving cancellation authority.
- Python =Task.cancelling()= is task-local, read-only to the consumer, and distinguishable from a completed =asyncio.timeout()= path.
- Therefore the smaller contract is one public =tool_cancellation_requested()= helper for async service-tool cleanup. It reports only whether the current tool task is under canonical cancellation. It exposes no token, principal, process id, target, callback, or cancellation mutation method.
- Concurrent invocations remain isolated by asyncio task ownership. Existing =ToolCancelled= remains the runtime terminal event and the existing =ToolNode= remains execution authority.

** Rejected alternatives
- Plugin-specific =shell.cancel=: second control plane and reusable external identifier.
- Model-visible cancellation token: lets untrusted tool arguments participate in control semantics.
- New principal/turn/tool-run context: unnecessary identity exposure for the required cooperative teardown signal.
- Direct =BaseTool= execution outside =ToolNode=: forks canonical execution behavior.

** RED / GREEN acceptance
- Before cancellation, a running tool observes false.
- During its =CancelledError= cleanup, the cancelled invocation observes true.
- Cancelling one concurrent invocation does not mark another invocation cancelled.
- A tool-local timeout is not reported as canonical cancellation.
- Existing approval, registry, =ToolNode= and =ToolCancelled= behavior remain unchanged.

** Evidence
- RED head =51ca33107f366c27859cc5cb269753d64d202ca7= established the missing Core surface.
- The initial identity-context implementation was deliberately removed after adversarial review selected the smaller task-local contract.
- Candidate implementation exports only =zara.plugins.tool_cancellation_requested= and does not modify =android/**=.
