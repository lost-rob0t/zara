#+title: RAGE #669 — silent turn-completion event loss

* Iteration 1
- Start commit :: =23ad58013f8590a88e3514165c39318d1a641b29= (master)
- Consumed issue :: [[https://github.com/lost-rob0t/zara/issues/669][#669]] — daemon silently drops turn-completion events; CLI clients hang until timeout

* Reproduction facts (2026-09-10, live host)
- Stall rate with wake listener + desktop connected: ~50% (3/6, then 1/3, then 2/3).
- Foreground isolated daemon (no clients): 6/6 turns complete.
- Fresh daemon + wake listener only: stalls appear within the first few turns
  (runs 2-5 stalled, run 1 and later runs completed).
- Wake listener stopped, fresh daemon: 6/6, 8/8 complete.
- Wake listener re-enabled: stalls return immediately.

* Instrumentation evidence (scripts/instrumented_server.py)
- Wrapped =RuntimeEventSubscription._put= (bus drop-oldest) and
  =ZaraZmqGateway._drop_route_locked=.
- Result over ~4 minutes with wake connected: **55 ROUTE DROPs, 0 bus drops**.
- Route drops alternate =audio_output=None= (probe client) and
  =audio_output=True= (wake listener negotiated audio output) — both clients'
  routes are being torn down repeatedly, not overflowing queues.
- Daemon DEBUG log during stalls shows ZAP/CURVE handshakes every ~7.5s = clients
  reconnecting; reconnect destroys =_RouteState=, so events for the dead route
  are silently =continue=-dropped (zmq_transport.py route-miss branch).

* Working hypothesis
Wake-client reconnect churn (or per-message route drops) tears down routes
mid-turn; the shared event subscription then drops turn events for routes that
no longer exist, silently. Terminal events must be delivered or surfaced, and
route teardown mid-active-turn must be logged loudly.

* Open questions
1. What triggers the repeated route drops? (outbound queue full →
   =_enqueue_outbound= drop, ZMQError send path, or hello re-negotiation on the
   same identity?)
2. Why does the wake client reconnect every ~7.5s after stalls?

* Iteration 2 — final shape after contract correction
- The repository enforces fail-closed permanent send errors
  (=t/test_zmq_send_diagnostics.py::test_permanent_outbound_error_remains_fail_closed_and_secret_safe=).
  Iteration 1's blanket "queue on any ZMQError" violated it and was reverted;
  =zmq.Again= keeps its retry-queue, permanent =ZMQError= keeps dropping the route.
- Root cause refinement: the 1s/3s ZMTP heartbeats killed connections whenever the
  host stalled >3s (load-41 host, LLM streaming), forcing reconnects; reconnect
  route teardown then orphaned in-flight turns silently (route-miss =continue=).
- Final change set (commit): heartbeat 10s/30s; overflow drops the oldest queued
  event instead of the route; =_drop_route_locked= warns with orphaned turn ids
  (secret-safe); silent gateway-loop death now logs =gateway loop terminated
  unexpectedly= (this exact silence hid the log crash during iteration 1).
