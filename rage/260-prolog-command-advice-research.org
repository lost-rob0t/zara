* Security and lifecycle analysis
A speech utterance must never select a callable Prolog goal. The only dynamic selection is by canonical resolved =Intent/Args= against trusted-local predicates loaded from the user-owned hook file. Override dispatch therefore remains local configuration authority, not a remote-code-execution API.

The policy is fail-closed: an override can run only when =hook_policy(true,true)=. If disabled or override permission is false, the existing =commands:execute/2= path remains unchanged.

A custom handler that simply fails is treated as not-handled so core execution can continue. A selected handler that throws is different: silently falling through could double-execute side effects, so the exception becomes a bounded =command_result(failure,...,exception(Error))= and core execution is not attempted.

* Alternatives rejected
- Shell-string command hooks: rejected; conflicts with structured capability ownership and expands injection surface.
- A second Prolog process/runtime: rejected; violates one-runtime ownership.
- Dynamically constructing callable goals from user speech: rejected; turns input into code.
- Treating =allow_override=true= alone as sufficient: rejected; both gates must be true.

* Selected slice
Add a dynamic/multifile =command_handler/2= extension point and =advice_command_loop/3=. Wire it immediately before the existing core =commands:execute/2= call. Keep result shape and reply ownership unchanged.
