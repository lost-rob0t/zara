* Research restart
- Zara already owns the exact post-approval/post-availability invocation in =create_tools_node()=: one validated tool call is converted to one =AIMessage= and passed through the canonical =ToolNode.ainvoke()= path.
- Cancellation terminal ownership already sits in the surrounding =gated_tools_node= =CancelledError= handler via typed =ToolCancelled(reason="turn cancelled")=.
- Therefore cancellation lifecycle should be bound at Zara's own exact invocation boundary, not delegated to a dependency interceptor whose context propagation has failed under the pinned stack.

* Selected r6 architecture
- Preserve ordinary =ToolNode(tools)= with no execution interceptor.
- After approval and unload/availability checks and immediately before the one exact =ToolNode.ainvoke()=, bind one private cancellation signal for that invocation.
- Run the canonical =ainvoke()= as the owned child task and shield it from outer cancellation long enough to set the cooperative signal first.
- On outer cancellation: signal first, cancel the owned child task, await its cancellation/cleanup, publish the existing single typed =ToolCancelled= terminal event, then re-raise.
- Expose only the read-only =ToolCancellation= view to plugin code. No model argument, process identifier, registry bypass, second runtime, or cancellation side channel.

* Adversarial invariants
- Rejected/unavailable tools never receive a cancellation scope.
- Concurrent invocations cannot signal one another.
- A plugin cannot set, replace, retarget, or suppress Core cancellation.
- Approval remains authoritative before execution.
- Tool result normalization and terminal events remain owned by the existing gated tools node.
- The implementation must work for both async tools and synchronous tools delegated by LangChain.

* TDD map

- RED-3 :: cancelling one concurrent invocation does not signal another.
- RED-4 :: rejected and unloaded tools never enter cancellation scope.
