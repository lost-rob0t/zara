* Iteration 1
** Research
- Dedicated artifact :: =rage/132-live-voice-research.org=.
- Current protocol already reserves voice/audio message families and already carries opaque binary multipart payloads, but audio messages have no message-specific semantic validation and the gateway returns =not_implemented=.
- Existing =StreamingVAD= consumes exactly 512 samples at 16 kHz; PCM s16le mono maps that directly to a 1024-byte / 32 ms wire frame.
- PyZMQ/ZeroMQ evidence confirms ROUTER/DEALER multipart framing is appropriate. The newer CLIENT/SERVER family disallows multipart messages, so replacing the established socket family would conflict with ZARA/1 binary audio.
- HWM is a message-count queue bound, not an application byte/utterance bound; per-stream lifecycle/sequence/resource limits remain mandatory.
- Research changed the inherited loose-chunk direction: baseline v1 input should use exact 32 ms PCM frames rather than variable chunks that force gateway buffering/reframing.

** Design
- Dedicated artifact :: =rage/132-live-voice-design.org=.
- Baseline ingress :: =pcm_s16le=, mono, 16 kHz, 512 samples / 1024 bytes per =audio.input.chunk=.
- Protocol layer validates message-local shape/geometry; principal/route-scoped stream state validates start/chunk/commit/cancel lifecycle and contiguous sequence numbers.
- Stream state is volatile and non-resumable across daemon restart; durable conversation continuity remains separate.
- Gateway validates/routes only. Existing runtime/StreamingVAD/TurnCoordinator paths own STT, cancellation, model/tool/TTS work.
- Barge-in must map to canonical turn cancellation and stale output filtering, not a daemon-only cancellation path.
