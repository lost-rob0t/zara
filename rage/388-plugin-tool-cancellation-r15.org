Do not revive its schema/argument transport.

* Research — iteration r15
** Current Core boundary
=create_tools_node= already owns the post-approval, current-registry-binding, per-tool-call boundary and still dispatches through one LangGraph =ToolNode=. This remains the authority for queue/start/terminal events.

** Upstream behavior relevant to the failure
LangChain =BaseTool= has public =invoke/ainvoke= execution entrypoints before its internal schema-to-=_run/_arun= dispatch. Existing upstream defects around =InjectedState=, =ToolRuntime=, dynamic tools and injected arguments mean #388 must not depend on ToolNode rewriting an extra plugin input field.

** Selected architecture
- Plugins opt into cooperative cancellation through explicit boolean tool metadata, not schema introspection.
- Core wraps an opted-in =BaseTool= once at registry binding. The same wrapper instance is therefore the object seen by the existing ToolNode and stale-binding identity check.
- The wrapper preserves the original public name/model-facing schema and delegates to the original =BaseTool=.
- Each wrapper invocation creates exactly one private cancellation signal after approval/current-binding checks have already allowed ToolNode execution.
- Plugin code observes only =current_tool_cancellation()=. There is no cancellation tool argument, hidden schema field, ID lookup, mutable shared slot, or plugin-specific cancel command.
- The unchanged =create_tools_node= remains terminal event authority; its existing =ToolCancelled(reason="turn cancelled")= is the sole terminal cancellation outcome.

** CI #1644 falsification and boundary correction
Exact-head candidate =0a81b4454c16273d4467826ae768026f51a463e1= ran 1987 Core tests and failed exactly four. Android compatibility and both shared-mic lanes were green; flake/package correctly skipped after Core failed.

Three failures were architecture-relevant and identical in shape: sync, async, and concurrent acceptance never reached the original plugin body. The fourth was not a cancellation failure: the spoof test expected an error =ToolMessage= even though canonical =create_tools_node= intentionally converts ToolNode exceptions into =RuntimeError("tool <name> execution failed")=.

The r15 wrapper had overridden internal =_run/_arun=. That left execution subject to BaseTool's wrapper-side schema dispatch before the cancellation wrapper body, reproducing the same pre-body boundary failure in a different form.

The corrected r15 seam overrides the wrapper's public =invoke/ainvoke= entrypoints instead. It forwards ToolNode's original input unchanged to the original BaseTool, letting the original tool remain sole owner of input validation/schema conversion. The cancellation token is bound around that original invocation inside the exact worker thread/task. Sync originals run through =asyncio.to_thread=; async originals run in an owned task. Parent cancellation is shielded only long enough to set the private signal before cancelling owned async execution and re-raising.

A new direct acceptance test first proves the registry-bound wrapper itself reaches the original body and exposes a real =ToolCancellation=. The spoof case now asserts canonical =RuntimeError= plus zero plugin-body entry; its security assertion is unchanged.

This is a bounded correction within the registration-wrapper architecture. If public =invoke/ainvoke= still cannot prove body reachability at exact head, retire r15 rather than adding another transport layer.

** Rejected alternatives
- =InjectedState= / =InjectedToolArg= / schema transport: falsified by r7-r14 and pinned-stack validation/injection behavior.
- Outer ToolNode =ContextVar=: falsified by r5/r6.
- Wrapper-internal =_run/_arun= transport: falsified by exact-head CI #1644 before plugin body entry.
- Mutable token stored on a shared tool instance: violates exact-invocation concurrency isolation.
- Plugin-specific cancel command/side channel: creates a second control plane.
- Direct plugin-function execution from graph: bypasses canonical BaseTool/ToolNode policy.
- Per-invocation ToolNode replacement: duplicates executor construction and has prior dynamic-tool failure evidence.

* Invariants
- Approval and current registry binding are checked before wrapped execution.
- Exactly one signal per exact tool invocation.
- Model arguments cannot provide, suppress, or retarget cancellation state.
- Concurrent invocations never share cancellation state.
- Sync and async plugin bodies can observe the token after body entry.
- Signal is set before cancellation propagates into owned async work.
- Unloaded/rejected tools never execute or receive a token.
- Non-opted-in tools remain unchanged.
- Malformed opt-in metadata fails closed before registry mutation.
- One canonical ToolNode path; no second executor/runtime/approval channel.

* Acceptance mapped to tests
- Explicit opt-in is model-schema neutral.
- Access outside an active invocation fails explicitly.
- Malformed metadata fails closed and does not partially register.
- Registry-bound wrapper directly reaches the original body with an invocation token.
- Sync plugin body reaches entry, sees =ToolCancellation=, and observes signal before side effect.
- Async plugin body reaches entry and sees signal set before =CancelledError=.
- Concurrent invocations have distinct token identities and cancellation isolation.
- Rejection/unload never enter plugin body.
- User/model arguments cannot spoof cancellation; invalid extra input is rejected by the original tool schema before body entry.
- Existing ordinary tool/approval/todo tests remain green.
