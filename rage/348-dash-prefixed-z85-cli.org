* Research / failure evidence
- Android transaction CI #1165 failed in Core test =t.test_security_threat_management::test_security_list_exposes_no_server_secret_or_zap_internal_user_id=.
- Generated client public key was =-.6(Vfv?M9JT!Y^l)iow0lAtnD(*w[0(d)(@EuI1=, a 40-character Z85 value beginning with =-=.
- =argparse= classified that next token as an option and raised =argument --security-enroll-key: expected one argument= before Zara's security validation ran.
- Shell quoting does not change this token classification. The equals form =--security-enroll-key=<key>= works, but relying on callers to discover that special case leaves generated valid keys nondeterministically unusable.
- The bug is in Core CLI parsing, not Android transport or CURVE/ZAP authorization.

* Architecture / adversarial decision
- Preserve one existing =zara-server= management parser and the current security state/admin implementation.
- Do not globally reinterpret unknown dash-prefixed tokens as values.
- Normalize only the closed =--security-enroll-key= option when its immediately following token has the exact Z85 public-key shape required by the security contract; then hand the normalized argv to ordinary argparse.
- Invalid length/alphabet remains ordinary malformed CLI/security input; unrelated unknown options retain argparse fail-closed behavior.
- No new key format, enrollment path, protocol message, or Android-specific parser.
